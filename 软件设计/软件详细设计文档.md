## 1 文档概述

### 1.1 编写目的

本文档是 ISA 模拟系统在软件详细设计阶段的正式产出，作用有三：

1. **把"黑盒子"变为"白盒子"**——《软件体系结构设计文档》给出了 7 个子系统与 35 个构件的职责边界，但每个构件内部"由哪些类组成、每个类有哪些属性和方法、它们如何协作完成一个用例"尚未落地。本文档补齐这一层，使设计细化到**程序员可直接编写代码**的程度。
2. **固化详细设计阶段的四类模型**——用例实现模型（设计类 + 用例设计顺序图）、类模型（设计类图 + 类方法活动图 + 类对象状态图）、数据模型（实体关系图 + 数据访问层类图 + 数据操作活动图）、构件模型（构件图 + 构件状态图 + 构件装配活动图）。
3. **建立自需求到设计的双向可追踪**——第 4~7 章逐层标注每条设计元素承载的需求编号，附录 B 给出反向索引，使"某个需求有没有人实现"与"某个类为什么存在"都能被快速核查。

本文档的读者为项目组全体成员、课程指导教师，以及后续接手编码实现与测试的人员。

### 1.3 术语定义

本文档沿用《软件需求规格说明书》1.3 的术语（ISA、RV32I、GPR、CSR、PC、ISA 描述文件、外部参考模拟器、对拍、架构状态、执行轨迹、终止序列、比对子集、边界类、控制类、实体类、工业芯片工程师）。另补充详细设计阶段引入的术语：

| 术语 | 含义 |
| --- | --- |
| **设计类** | 详细设计阶段对分析类精化后的类，给出属性类型、方法签名、可见范围与实现算法 |
| **构造型（stereotype）** | 类图中标注类角色的记号，本文档使用 «service» «entity» «component» «adapter» «dao» «view» «store» «struct» «factory» «interface» «abstract» |
| **值类型** | 无行为的纯数据载体，按值传递，成员全开 |
| **数据实体类** | 需要持久保存的数据持有者，本身无行为，对应第 6 章的库表 |
| **运行上下文（RunContext）** | 一次程序执行的独占上下文，持有内核、轨迹、起始时间与剩余限额；**一次性对象** |
| **译码表（DecodeTable）** | 由 ISA 描述文件在装载期编译出的指令译码表；内核经 `IDecodeTable` 使用它 |
| **执行层语义（InsnSemantic）** | 内核可理解的指令语义描述（语义类别 `OpClass` + 字段位置 + 立即数来源），与描述层的字符串/位域表示分离 |
| **组合根（Bootstrapper）** | 全系统唯一的构件装配点，双形态差异在此一次性决定 |
| **UPSERT** | `INSERT … ON CONFLICT … DO UPDATE`，两形态数据库同语法 |
| **归属谓词** | 每条涉及用户数据的 SQL 都携带的 `uid` / `ws_id` 条件，是多用户隔离的实现手段 |
| **L5 边界** | 新增指令若落在既有 10 类 `OpClass` 之内属纯数据工作；需要新语义类别时须扩展内核模板表（见 7.6） |

## 2 系统概述

### 2.1 系统目标

本系统是一个**纯软件的 ISA 模拟系统**，以解释执行的方式重建指令级行为，并提供可视化、可调试、可批量验证、可与外部参考模拟器比对的能力。系统在执行内核与指令集定义之间保留抽象边界，指令的格式与语义以 ISA 描述文件形式提供，**内核不硬编码具体指令**。

四类用户对应四类目标：

| 编号 | 业务目标 | 对应问题 | 主要承载用例 |
| --- | --- | --- | --- |
| G1 | 让 ISA 学习者在无硬件条件下，以可视化单步的方式理解指令语义 | 指令执行过程不可观察 | UC-03~UC-06 |
| G2 | 让工业芯片工程师在秒级完成指令级功能冒烟验证，不依赖 EDA 工具链 | 指令级功能验证成本高 | UC-08、UC-09、UC-13 |
| G3 | 让 ISA 工程师通过两套独立实现的行为对拍，发现规范本身的歧义与不一致 | 指令集规范歧义难以发现 | UC-02、UC-10、UC-11 |
| G4 | 让机器语言程序员在可回退、可重放的模拟环境中调试裸机程序 | 裸机调试环境缺失 | UC-04~UC-07、UC-12 |

### 2.2 主要功能

系统功能分为九组，共 38 条功能需求：

| 功能组 | 内容 | 需求编号 | 主要承载子系统 |
| --- | --- | --- | --- |
| ISA 描述装载与管理 | 描述文件的解析、校验、装载、激活与切换 | FR-1.1 ~ FR-1.3 | SS-2 |
| 程序装载与运行配置 | 汇编源或机器码装载、基址与初态配置、示例程序集 | FR-2.1 ~ FR-2.4 | SS-5、SS-4 |
| 指令解释执行 | 取指—译码—执行—写回循环，架构状态维护与轨迹记录 | FR-3.1 ~ FR-3.5 | SS-1 |
| 调试控制 | 单步、连续执行、暂停、复位、断点、状态与轨迹查看、历史回退 | FR-4.1 ~ FR-4.4 | SS-5、SS-1 |
| 状态可视化 | 寄存器、内存、反汇编、执行轨迹四类视图与变化高亮 | FR-5.1 ~ FR-5.4 | SS-7、SS-6 |
| 批量测试与判定 | 用例集组织、批量执行、两种判定模式、报告与失败现场 | FR-6.1 ~ FR-6.5 | SS-5、SS-3 |
| 一致性对拍 | 调用 Spike 获取逐步状态、按子集比对、分歧记录与归因 | FR-7.1 ~ FR-7.5 | SS-5、SS-4、SS-3 |
| 集成 API | HTTP/WebSocket 接口、鉴权、限额、结构化响应 | FR-8.1 ~ FR-8.3 | SS-6 |
| 账号·工作区·配额 | 注册登录、会话隔离、工作区保存加载、账号与配额管理 | FR-9.1 ~ FR-9.5 | SS-5、SS-6 |

### 2.5 范围与边界

**本期范围**：ISA 描述装载与校验（首期 RISC-V RV32I）、程序装载与运行配置、指令解释执行、终止与运行期异常处理、指令级单步与断点调试、寄存器与内存可视化、示例程序与新手引导、测试用例组织与批量验证、与 Spike 的一致性对拍、集成 API、多用户会话与隔离。

**本期不在范围内**：周期精确的微架构建模；完整外设与中断建模；操作系统级全系统仿真；第二套指令集的完整实现（仅保留 ISA 抽象边界）；QEMU 等其他参考模拟器的接入；`riscv-arch-test` 特权模式测试套件的整体接入。

**边界划分**：由本软件实现的有指令语义解释、架构状态维护、调试控制、状态可视化、示例程序、测试编排与判定、对拍调度与差异归因、API 服务、用户与会话管理；由环境或第三方提供的有浏览器渲染容器、宿主操作系统、外部汇编工具链、Spike、Git 托管服务。

## 3 设计目标和原则

### 3.1 详细设计欲达成的目标

体系结构设计回答了"系统由什么组成、如何分层"（T1~T8）。详细设计要在此基础上达成下面六条可检验的目标：

| 编号 | 详细设计目标 | 检验方式 |
| --- | --- | --- |
| D1 | **每个用例都有确定的实现方案**：14 个用例各自给出参与的设计类、方法签名级消息序列与异常/拒绝出口 | 4.3 逐用例方案 + UD-01~UD-14 顺序图 |
| D2 | **每个类都细化到可编码**：属性有名有型有初值，方法有签名、功能、前置与后置条件，复杂方法有活动图 | 5.4~5.7 的表；`活动图-EmulatorCore-step.svg` 等 3 张 |
| D3 | **每条需求都能落到设计元素**：38 条功能需求 + 13 条质量与约束需求无悬空项 | 附录 B 需求追踪矩阵 |
| D4 | **持久数据有确定的库表与操作**：12 张表、88 个字段、15 条外键；读写改删验证各有落点 | 第 6 章 + `数据模型-实体关系图.svg` |
| D5 | **跨子系统依赖单向无环**，且可被构建脚本断言而非靠口头约定 | `构件图-构建产物与链接方向.svg` 的四条构建断言 |
| D6 | **架构层面的问题在设计阶段解决**，不留到编码阶段 | 7.6 的四条评审修正（DD-11 ~ DD-14） |

### 3.2 关键需求对详细设计的决定作用

| 需求 | 对详细设计的决定作用 | 设计落点 |
| --- | --- | --- |
| FR-1.1 / NFR-I1（描述驱动，新增 ISA 不改内核） | 内核不得认识 `funct7`、掩码与描述文件格式，译码必须经接口倒置 | `IDecodeTable` + `InsnSemantic` + `OpClass`（7.6 DD-11） |
| NFR-I2（内核可独立编译为库） | 内核静态库链接依赖归零，构建脚本断言而非约定 | 断言 A / D；`libisa_core` 只链 C++ 标准库 |
| NFR-Q1（10⁷ / 10⁶ 条每秒） | 轨迹记录必须可整体关断；单步链路不得引入异步 | `Trace::enable()`；`CoreFactory::create(traceEnabled)` 单点控制；不引入消息队列 |
| NFR-Q2（单用例失败不影响其余） | 每用例必须持有独立内核实例与独立轨迹 | `RunContext` 一次性对象 + `CoreFactory` 唯一创建点 + 用例串行执行 |
| NFR-Q5 / FR-9.5（不可信输入、用户隔离） | 限额前置到请求入口；数据隔离靠归属谓词 | 7.6 DD-13；6.8 归属谓词三条规则 |
| FR-6.5 / FR-7.2（两种判定模式复用同一引擎） | 比对能力必须是**跨用例复用的独立构件**，不得内联进服务 | `CompareEngine` 自分析类 → SS-3 → 设计类三级同名（5.5 关系 #31） |
| FR-8.1 / NFR-C1（HTTP 契约、C++ 与 Web 跨语言） | 对外契约必须尽早冻结，前端不得链接内核 | SS-6 的 REST/WS 契约（冻结级）；构建断言 C |
| NFR-C3（5 人一学期） | 构件粒度偏粗，不做过早拆分 | 7.6「故意不做的优化」三条 |

### 3.3 详细设计遵循的原则

在体系结构七条原则（P1~P7）之下，详细设计追加五条操作化原则：

| 编号 | 原则 | 落实方式 | 可核查点 |
| --- | --- | --- | --- |
| DP1 | **可见范围最小化** | 属性一律 private / protected；实现细节方法一律 private；值对象成员全开是有意例外 | 5.4；30 个 private 方法 |
| DP2 | **依赖抽象而非具体类** | 服务之间一律经 `IStore` / `IComparator` / `ICoreService` / `ICoreFactory` / `IDecodeTable` / `IToolchainPort` / `IRefSimPort` | 5.5 关系表第 1、10、16、20、21、25、26、31 行 |
| DP3 | **一个类一个变更原因** | `QuotaGuard` 只管限额、`AuthFilter` 只管鉴权、`IsaValidator` 只管校验、`IsaSpec` 只管格式 | 7.3 各子系统构件表 |
| DP4 | **创建与使用分离** | 内核只由 `CoreFactory` 创建；单例只由 `Bootstrapper` 装配 | 5.8 两条硬约束 |
| DP5 | **契约优先于实现** | 接口稳定性分三级（冻结 / 稳定 / 可演进），迭代一冻结的接口表面积被主动压小 | 5.4 接口清单；7.6 DD-12 |

### 3.4 现实限制与应对

| 编号 | 限制 | 对详细设计的影响 | 应对落点 |
| --- | --- | --- | --- |
| L1 | 5 人一学期工作量上限 | 子系统 7 个不再细分；第二套 ISA 与 QEMU 接入只留扩展点 | 7.6「故意不做的优化」 |
| L2 | Spike 的状态可见性受 `--log-commits` 格式限制且格式非本项目可控 | 解析器必须容错，且必须有降级路径 | `RefSimAdapter::parseCommits()` 容忍未知行与缺失字段；FR-7.5 降级为终态断言 |
| L3 | 汇编与反汇编依赖外部工具链 | 工具链缺失时必须明确提示而非静默失败；适配层要处理输出差异 | `ToolchainAdapter::assemble()` 返回结构化错误清单 |
| L4 | `riscv-arch-test` 特权模式测试超出本期范围 | 不整体接入，仅取非特权子集或自编用例 | 7.6 决策 DD-9 |
| L5 | 无独立生产级云主机预算 | 云端形态保持轻量（单机三容器） | 部署视点 |
| L6 | 无遗留系统可复用 | 全部构件新开发 | 第 7 章全部构件表 |
| **L7** | **语义模板表的扩展边界** | 新增指令若落在既有 10 类 `OpClass` 之内是纯数据工作；需要新语义类别时仍须扩展内核模板表 | 7.6 DD-11 的限制说明；建议以"新增一条 RV32I 之外但类别已知的指令"作为验收判据 |

### 4.2 分析类到设计类的转换方式

按技能规定的三种转换方式归类：

- **方式一**——一个分析类的一项职责，由一个设计元素的**单个方法**完整实现；
- **方式二**——一个分析类的一项职责，由一个设计元素的**多个方法**实现；
- **方式三**——一个分析类的一项职责，由**多个设计元素协作**完成。

| 分析类 | 职责 | 设计元素 | 方式 | 说明 |
| --- | --- | --- | --- | --- |
| `SessionController` | 凭据校验、开会话、建隔离工作区 | `SessionService` | 方式二 | `login()` / `createSession()` / `createWorkspace()` |
| `SessionController` | 列出用户与资源占用 | `SessionService` + `WorkspaceService` | **方式三** | 账号数据与会话数据归属不同服务 |
| `IsaController` | 校验 ISA 描述 | `IsaValidator` | 方式一 | `validate()` 单方法完整实现 |
| `IsaController` | 装载并切换当前 ISA | `IsaRegistry` + `IsaSpec` + `DecodeTable` | **方式三** | `install()` 编排 parse → validate → build |
| `LoadController` | 汇编转码 | `ToolchainAdapter` | 方式一 | `assemble()` 单方法 |
| `LoadController` | 按基址载入并初始化 | `LoadService` + `ProgramImage` + `EmulatorCore` | **方式三** | 载入与初始化分属不同构件 |
| `DebugController` | 单步 / 运行 / 暂停 / 复位 | `DebugService` | 方式二 | 四个方法对应四种运行控制 |
| `DebugController` | 断点登记与命中检查 | `DebugService` + `BreakpointTable` | **方式三** | 流程在服务、数据在断点表 |
| `TestController` | 批量执行、判定、汇总 | `TestService` + `Persistence` + `CompareEngine` | **方式三** | 流程、持久化、比对三方协作 |
| `DiffController` | 驱动双方执行并比对 | `DiffService` + `EmulatorCore` + `RefSimAdapter` + `CompareEngine` | **方式三** | 系统内最长的跨构件协作链 |
| `ApiController` | 解析、鉴权、限额、分发、封装 | `HttpGateway` + `AuthFilter` + `QuotaGuard` | **方式三** | 按三个变更原因拆分 |
| `ApiEndpoint` | 请求接收与响应回送 | `HttpGateway` | 方式一 | `handle()` 单方法 |
| `ApiEndpoint` | 状态增量推送 | `StatusChannel` | 方式一 | `push()` 单方法 |
| `EmulatorCore` | 取指—译码—执行—写回 | `EmulatorCore` + `ProgramImage` + `IDecodeTable` + `ArchState` + `Trace` | **方式三** | 管道四级由不同构件承担，内核仅编排 |
| `EmulatorCore` | 终止与异常判定 | `TrapUnit` | 方式一 | `check()` 单方法 |
| 7 个服务类 | 日志、配置、事务模板 | `ServiceBase` | **方式三** | 消除 7 处重复样板 |
| `TestController` / `DiffController` | 内核实例创建 | `CoreFactory` | **方式三** | 集中创建点，NFR-Q2 的落点 |
| 各 `*View` | 界面呈现 | 对应前端视图类 | 方式二 | 渲染与交互各为独立方法 |

**统计**：方式一 6 项、方式二 4 项、方式三 10 项（其中 2 项在本阶段新增）。**方式三占比接近一半**，这与体系结构把系统拆成 7 个子系统直接相关——跨子系统协作只能由多个元素共同承担，不是设计阶段的额外复杂化。

### 4.5 用例设计中确立的三条实现约束

1. **`RunContext` 是 NFR-Q2 的唯一落点。** 批量测试中"每用例独立上下文"落到代码上就是 `TestService` 为每个用例 `new RunContext(core, archState, trace)`。若图省事共享一个 `EmulatorCore`，单个用例越界或死循环会污染后续用例，可靠性需求即失效。
2. **`Trace` 的回退能力决定 `ArchState` 的存储策略（UC-07）。** 两种实现：①每步存完整快照（内存开销 O(n × 状态大小)，实现最简）；②存可逆增量（内存小，但要求每条指令的操作可逆，RV32I 中 `ecall` 等侧效指令需特判）。详细设计取 ①，并把"轨迹可关断"（NFR-Q1）作为性能开关。
3. **`RefSimAdapter` 的解析容错（限制 L2）。** Spike 的 `--log-commits` 输出格式非本项目可控，解析器必须容忍未知行、缺失字段与版本差异，并返回"部分可比"而非直接失败——否则 FR-7.5 的降级路径无从触发。

### 5.4 可见范围策略与接口清单

技能要求"尽可能缩小可见范围，遵循信息隐藏原则"。本设计采用**三档 + 一处例外**：

| 档位 | 适用范围 | 数量级 |
| --- | --- | --- |
| **public** | 类的构造与析构、对外契约方法（接口实现方法、被其他子系统调用的方法） | 约 78% |
| **private** | 实现细节：管道各级、校验子检查、解析器内部函数、脏页标记等 | 约 22%（**30 个方法**） |
| **protected** | 仅 `ServiceBase` 的 `m_log` / `m_cfg` 与模板方法 `withTransaction()` / `log()` | 2 属性 + 2 方法 |
| 例外 | 值对象（«struct»）成员全部 public | `StepResult`、`InsnDef`、`StateRecord` 及 5.7 的 31 个值类型 |

**三处需说明的判断**

1. **类级可见范围全部为 public，不用 `friend` 也不做内部类。** 语言层面 C++ 的类默认可见性不构成封装边界（同一静态库内一律可互相引用），真正的边界由**构建脚本**强制：内核静态库 `libisa_core` 不链接任何网络 / JSON / 数据库库，跨库引用即链接失败。这是把 NFR-I2 从"口头约定"变成"编译期约束"的落点。
2. **protected 缺省不用，是因为类间不存在泛化。** 分析阶段已裁定：用例图里四类用户对"注册用户"的泛化是**执行者层**的泛化，不得映射成类继承。全系统唯一的继承链是 7 个领域服务 → `ServiceBase`，protected 就落在这条链上。
3. **值对象成员公开是有意为之。** `StepResult` 这类对象没有不变式需要保护（拿到即读）；判据是「**有无需要维护的不变式**」，不是「数据还是行为」。

### 5.5 属性精化

属性形式的三条规则：

1. **按语义选形式**：生命周期与持有者一致 → 裸指针/值成员（组合）；可独立存在且由外部创建 → `const T*` 只读指针（关联）；可变行为策略 → `T*`（依赖注入）。
2. **只读优先**：凡跨模块共享的数据一律 `const`，把"只读"变成**类型级**约束而非约定（`m_prog`、`m_decode`、`m_bp`、`m_cmp`、`m_store`）。
3. **集合一律用标准容器且不暴露内部**：`vector` / `map` 私有，对外走 `range()` / `all()` 等返回**副本**的方法。

**两条硬约束**

1. **禁止在业务代码里直接 `new EmulatorCore`。** 内核实例必须经 `CoreFactory` 创建——这是 NFR-Q2「用例之间互不影响」在代码层面的唯一保证点，也是后续若要换成进程隔离时唯一需要改的位置。
2. **`RunContext` 是「一次性」对象**，`drop()` 后再使用属于编程错误（`状态图-RunContext.svg` 中 `Disposed` 不可回到 `Running`）。批量执行中图省事共享一个上下文，会直接导致 NFR-Q2 失效。

## 6 数据设计

### 6.1 持久化对象判定

**判定口径**：一个类需要持久化，必须同时满足两条——①**需求要求它跨会话存在**（进程重启后用户仍能看到它）；②**它没有更便宜的载体**（若能从别的持久数据推导出来，就不落库）。

按此口径，**52 个设计类中只有 12 个需要持久化**。下列类别不持久化：

| 组 | 类 | 不持久化的理由 |
| --- | --- | --- |
| 内核运行时状态 | `EmulatorCore`、`ArchState`、`Trace`、`TrapUnit`、`StepResult`、`RunContext` | 生命周期与一次执行绑定（`RunContext` 是**一次性对象**）；需要留存的只是它们的**快照**，而快照已由 `divergence` / `case_result` 以 JSON 承载 |
| 内存态译码表与注册表 | `DecodeTable`、`IsaRegistry`、`IsaValidator`、`InsnDef`、`InsnSemantic`、`OpClass` | 由描述文件（`isa_meta.path`）**可重建**，落库只会造成「库与文件不一致」；落库的只有元数据 |
| 进程内索引与配置 | `BreakpointTable`、`AuthFilter` 票据缓存、`StatusChannel` 连接表、`QuotaGuard` 限额、`DbConfig`、`RunSpec` | 前两者是**运行期索引或连接句柄**（断点本身已落 `breakpoint` 表），后几项是配置与实时占用 |
| 前端与适配器 | 8 个视图类、`HttpApiClient`、`StateStore`、`ToolchainAdapter`、`RefSimAdapter`、`ProcessRunner`、`Bootstrapper` | 前端状态随页面销毁；适配器只持有路径与超时等配置 |
| 服务与比对 | 7 个领域服务、`ServiceBase`、`CompareEngine`、`DiffScope` | 无状态或有状态但无跨会话意义 |

### 6.2 存储机制选择

**选择关系数据库而非数据文件。** 理由有三：①需求存在明确的多用户隔离与配额统计（FR-9.5、NFR-Q5），关系库的外键与聚合查询是最直接的落点；②需要按条件查询（某个用户的历史报告、某个 ISA 被哪些用例集引用），文件方案需自行实现索引；③关系库能在 DB 层提供不可绕过的约束兜底（主键、唯一、外键、`CHECK`）。

**双驱动分工**：`DbDriver` 抽象之下两个实现——`PgDriver`（云端，带连接池）与 `SqliteDriver`（本地，WAL 模式 + `busy_timeout`）。这是设计目标 T8「双形态功能对等」在数据层的落点。

**差异收敛清单**（保证一套 DML 跑两种形态）

| 差异点 | 收敛方式 |
| --- | --- |
| 自增主键 | DDL 分两份（`BIGSERIAL` vs `INTEGER PRIMARY KEY AUTOINCREMENT`），应用层不感知 |
| 时间类型 | **统一存 `BIGINT`（UTC 毫秒）**，彻底消除 `TIMESTAMPTZ` vs `TEXT` 差异 |
| 布尔 | `BOOLEAN`（两形态均支持） |
| 二进制 | `BLOB`（两形态语义一致） |
| JSON | **存 `TEXT`**，不用 `JSONB` / `json` 函数，应用层负责序列化 |
| 枚举 | `SMALLINT` + `CHECK` 值域，不用 PostgreSQL 原生 `ENUM`（SQLite 无此类型） |
| UPSERT | `ON CONFLICT … DO UPDATE` —— **两形态同语法**，DML 因此只有一套 |
| 占位符 | PostgreSQL `$1`、SQLite `?`，由驱动的 `Dialect` 处理；`Persistence` 不做 SQL 拼接 |

**`test_case` 测试用例**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `case_id` | BIGINT | — |
| FK | `suite_id` | BIGINT | → `test_suite.suite_id`，`ON DELETE CASCADE` |
| FK | `prog_id` | BIGINT | → `program.prog_id`，**`ON DELETE RESTRICT`** |
| | `name` | VARCHAR(128) *可空* | — |
| | `judge_mode` | SMALLINT | 0 = FinalSnapshot，1 = CommitLog（FR-6.5 两模式） |
| | `insn_limit` | BIGINT | 0 = 不限；否则为该用例的指令条数上限（NFR-Q5） |

| | `expect_commits` | TEXT *可空* | `judge_mode = 1` 时非空：`StateRecord[]` 的 JSON |

约束：

- `CHECK ((judge_mode = 0 AND expect_final IS NOT NULL) OR (judge_mode = 1 AND expect_commits IS NOT NULL))` —— **两种期望态互斥且必居其一**，把 FR-6.5 的「两者都支持」从口头约定变成 DB 层约束；

**`test_report` 执行报告**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `report_id` | BIGINT | — |
| FK | `suite_id` | BIGINT | → `test_suite.suite_id`，`ON DELETE CASCADE` |
| | `judge_mode` | SMALLINT | 本次执行采用的判定模式（**有意冗余**，见 6.9） |
| | `total` | INT | 用例总数 |
| | `passed` | INT | 通过数 |
| | `started_at` / `finished_at` | BIGINT | `finished_at` 可空 = 执行中断（NFR-Q2 异常隔离下仍留痕） |
| | `triggered_by` | VARCHAR(64) *可空* | 触发者标识（UID 或 CI 客户端），对应 FR-6.4 |

约束：`CHECK (passed <= total)`、`CHECK (passed >= 0)`。

> **报告是「只增不改」的**：每次执行新增一行，历史报告永久保留（FR-6.3 要求可回溯）。这也让并发执行同一用例集无需互斥——两个请求各自写自己的报告行。

**`case_result` 失败现场**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK/FK | `report_id` | BIGINT | → `test_report.report_id`，`ON DELETE CASCADE` |
| PK/FK | `case_id` | BIGINT | → `test_case.case_id`，`ON DELETE CASCADE` |
| | `verdict` | SMALLINT | 0 = Pass，1 = Fail，2 = Partial |
| | `snap` | TEXT *可空* | 失败现场 `Snapshot` 的 JSON |
| | `diff_step` | BIGINT *可空* | 首个差异步号 |
| | `diff_field` | VARCHAR(64) *可空* | 差异字段名 |
| | `ours_val` / `ref_val` | VARCHAR(64) *可空* | 双方取值（字符串化，便于直接展示） |

> **只存失败用例**：与类设计「`m_failures` 仅存失败用例，通过的只计数」严格一致；**「失败」= `verdict != Pass`**，因此 `Partial`（基准不可用时的降级判定，结果需人工复核）同样计入本表 —— 否则报告无法解释「为什么某些用例没有结论」。
>
> 1000 个用例全部通过时本表写 0 行，报告表只写 1 行——这是 NFR-Q1 吞吐指标在落库环节的直接体现。

**`isa_meta` ISA 描述元数据**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `spec_id` | BIGINT | — |
| UQ | (`name`, `version`) | — | 同一 ISA 同一版本只登记一次 |

| | `xlen` | SMALLINT | 本期恒 32 |

> **本表全局共享、不带 `uid`**：ISA 描述是系统级资产而非用户数据。若后续要支持私有 ISA，只需加一列 `uid`（可空 = 全局），不影响现有查询。

**`divergence` 对拍分歧**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `div_id` | BIGINT | — |
| FK | `uid` | BIGINT | → `user.uid`，`ON DELETE CASCADE`；**保证分歧记录也受多用户隔离** |
| FK | `prog_id` | BIGINT | → `program.prog_id`，`ON DELETE CASCADE` |
| FK | `spec_id` | BIGINT | → `isa_meta.spec_id`，`ON DELETE RESTRICT` |
| | `step_no` | BIGINT | 首个分歧的指令序号 |
| | `scope_json` | TEXT | `DiffScope` 四要素的 JSON（PC / GPR / 内存写 / CSR 各是否参与） |
| | `ours_snap` | TEXT | 本内核侧 `StateRecord` 的 JSON（1:2 组合的第一份） |
| | `ref_snap` | TEXT | 基准侧 `StateRecord` 的 JSON（第二份） |
| | `fields_json` | TEXT *可空* | `DiffField[]` 的 JSON（差异字段明细） |
| | `tag` | SMALLINT | 0 = Unclassified，1 = ImplDefect，2 = RefDeviation，3 = SpecAmbiguity |
| | `note` | VARCHAR(512) *可空* | 人工备注 |
| | `created_at` | BIGINT | — |

> **落库 `scope_json` 的理由**：UC-11 重新打开一条历史分歧时，用户看到的不只是「差在哪一步」，还有「当时按什么口径比对的」。缺了它，同一步在两种 scope 下可能一个判「一致」一个判「分歧」，历史记录会变得无法解释。
>
> `tag` / `note` 是 **可 UPDATE 的少数列之一**（`annotate()`，FR-7.4 要求归因可复用），其余列只读。

**`breakpoint` 断点**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `bp_id` | BIGINT | — |
| FK | `prog_id` | BIGINT | → `program.prog_id`，`ON DELETE CASCADE` |
| UQ | (`prog_id`, `addr`) | — | 同一程序同一地址只有一条断点 |
| | `addr` | BIGINT | 断点地址（uint32 → BIGINT） |
| | `enabled` | BOOLEAN | 启停状态 |
| | `note` | VARCHAR(256) *可空* | — |

> 断点挂在**程序**而不是工作区上：同一程序在不同工作区里的断点语义相同，挂在工作区会导致同一映像出现多份互相矛盾的断点集合。

#### 6.3.3 关系落点汇总（15 条外键）

> 类设计给出 10 条持久化关系；落地时**新增 5 条**（标 ★），全部是外键可表达的关系。

| # | 关系 | 基数 | 落点 | 外键位置 |
| --- | --- | --- | --- | --- |
| 1 | `User` — `Session` | 1 : 0..n | `session.uid` | n 端 |
| 2 | `User` — `Workspace` | 1 : 0..n | `workspace.uid` | n 端 |
| 3 | `Workspace` — `ProgramRecord` | 1 : 0..n | `program.ws_id` | n 端 |
| 4 | `Workspace` — `TestSuite` | 1 : 0..n | `test_suite.ws_id` | n 端 |
| 5 | `TestSuite` — `TestCase` | 1 : 0..n | `test_case.suite_id` | n 端 |
| 6 | `ProgramRecord` — `TestCase` | 1 : 0..n | `test_case.prog_id` | n 端（RESTRICT） |
| 7 | `TestSuite` — `TestReport` | 1 : 0..n | `test_report.suite_id` | n 端 |
| 8 | `TestReport` — `CaseResult` | 1 : 0..n | `case_result.report_id` | n 端 |
| 9 | `TestCase` — `CaseResult` | 1 : 0..n | `case_result.case_id` | n 端 |
| 10 | `TestSuite` — `IsaMeta` | **n : m** | **`suite_isa` 交叉表** | 交叉表两端 |
| 11 | `Divergence` — `StateRecord` | 1 : 2 | `divergence.ours_snap` / `ref_snap` | **不建行，JSON 列承载** |
| 12 ★ | `Divergence` — `User` | n : 1 | `divergence.uid` | n 端 |
| 13 ★ | `Divergence` — `ProgramRecord` | n : 1 | `divergence.prog_id` | n 端 |
| 14 ★ | `Divergence` — `IsaMeta` | n : 1 | `divergence.spec_id` | n 端 |
| 15 ★ | `ProgramRecord` — `Breakpoint` | 1 : 0..n | `breakpoint.prog_id` | n 端 |

**三条落点规律**

1. **1:1 并入主表**：`User` — `Quota` 没有独立表，三个配额列直接进 `user`。
2. **1:n 外键建在 n 端**：上表 1~9、12~15 共 13 条 1:n 关系，外键一律建在子表；**子表恒为「多」的那一侧**。
3. **n:m 新增交叉表**：全系统只有 `TestSuite` — `IsaMeta` 一条 n:m，落在 `suite_isa`。

#### 6.3.4 索引设计

| 表 | 索引 | 类型 | 支撑的查询 |
| --- | --- | --- | --- |
| `user` | `name` | 唯一 | 登录（UC-01） |
| `session` | `token` | 主键 | 每次请求的鉴权（FR-8.2，**最热路径**） |
| | `uid` / `expires_at` | 普通 | 按用户统计会话数（配额）/ 空闲会话回收 |
| `workspace` / `program` / `test_suite` | (`uid`,`name`) / (`ws_id`,`name`) | 唯一 | 重名检查、按父对象列举 |
| `test_case` | `suite_id` / `prog_id` | 普通 | 用例集展开、按程序反查引用（RESTRICT 检查） |
| `test_report` | (`suite_id`, `started_at` DESC) | 复合 | 历史报告列表按时间倒序（UC-09） |
| `case_result` | (`report_id`,`case_id`) / `case_id` | 主键 / 普通 | 报告内定位失败用例 / 某用例历史失败记录 |
| `suite_isa` | (`suite_id`,`spec_id`) / `spec_id` | 主键 / 普通 | 用例集的 ISA 集合 / RESTRICT 检查 |
| `isa_meta` | (`name`,`version`) / `content_hash` | 唯一 / 普通 | 重复装载判定（UC-02） |
| `divergence` | (`uid`,`created_at` DESC) / `prog_id` / `tag` | 复合 / 普通 | 分歧历史列表（UC-11）、按程序反查、按归因筛选 |
| `breakpoint` | (`prog_id`,`addr`) | 唯一 | 断点去重；程序装载时一次性取全部断点 |

**索引取舍**：不为「看起来可能有用」的列建索引。`program.image`（大 BLOB）绝不建索引，`test_case.expect_commits` 也不建——两者的访问一律是「按主键取出整行」。

#### 6.3.5 约束设计（DB 层兜底）

| 约束类型 | 实例 | 意图 |
| --- | --- | --- |
| 主键 | 12 张表全部有主键（其中 2 张为复合主键） | 行唯一标识 |
| 唯一 | `user.name`、`session.token`（主键兼任）、(`uid`,`name`)、(`ws_id`,`name`)×2、(`name`,`version`)、(`prog_id`,`addr`) | 把「重名 / 重复登记」挡在 DB 层 |
| 外键 + `ON DELETE` | 15 条 | 完整性；`CASCADE` 用于「子数据随父数据无意义」，`RESTRICT` 用于「删父会静默毁掉用户资产」 |
| `CHECK` | `test_case` 期望态互斥；`test_report.passed <= total`；`passed >= 0` | 领域不变式 |
| 枚举值域 `CHECK` | `role ∈ {0,1}`、`status ∈ {0,1}`、`judge_mode ∈ {0,1}`、`verdict ∈ {0,1,2}`、`tag ∈ {0..3}` | 防止写入未定义枚举 |
| `NOT NULL` | 除标注「可空」的列外全部非空 | 避免应用层到处判空 |

### 6.4 数据操作说明

#### 6.4.1 按用例的操作序列

**UC-12 保存工作区**（见 `活动图-工作区保存落库.svg`）

| 步 | 操作 | 语句形（参数化） | 事务内 |
| --- | --- | --- | --- |
| ① | **验证**归属 | `SELECT uid FROM workspace WHERE ws_id = ?` | 否 |
| ② | **读取**占用 | `SELECT COUNT(*), COALESCE(SUM(LENGTH(image)),0) FROM program p JOIN workspace w ON p.ws_id=w.ws_id WHERE w.uid = ?` | 否 |
| ③ | 开启事务 | `BEGIN` | — |
| ④ | **写入**工作区 | `INSERT INTO workspace (uid,name,created_at,updated_at) VALUES (?,?,?,?) ON CONFLICT (uid,name) DO UPDATE SET updated_at = ?` | 是 |

#### 6.4.3 事务边界

| 事务 | 范围 | 隔离级别 | 理由 |
| --- | --- | --- | --- |
| 工作区保存（UC-12） | ④⑤⑥ | READ COMMITTED（两形态默认） | 四类 UPSERT 必须整体成功或整体失败，否则出现「程序有了、用例集没有」的半写状态 |
| 报告落库（UC-08） | ⑦⑧ | READ COMMITTED | 报告行与失败现场行必须同生共死 |
| 单条读 | 无显式事务 | 自动提交 | 避免长连接占用 |
| 会话创建 | 单语句 | 自动提交 | 无跨表约束 |

**事务模板方法**：`ServiceBase::withTransaction(fn)` —— 正常返回则 `COMMIT`，抛异常则 `ROLLBACK` 并继续上抛。所有跨表写操作都在这个模板里执行，**没有任何一处业务代码手写 BEGIN/COMMIT**，避免漏回滚。

#### 6.4.4 多用户隔离的实现方式

**隔离不靠数据库权限，靠每条语句的归属谓词。** 三条规则：

1. **每个涉及用户数据的查询都带 `uid` 或 `ws_id` 条件**——`WHERE prog_id = ? AND uid = ?` 而非先查后判。
2. **归属链全程可追**：`uid → workspace → program / test_suite → test_case → test_report → case_result`。任何子表的行都能沿外键回到 `uid`，不存在「孤儿行」；`divergence` 通过自身 `uid` 列直接归属。
3. **写操作先验证归属再写**：UC-12 第 ① 步校验不通过连事务都不开。
4. **两条归属链必须一致**：`divergence` 同时带 `uid` 与 `prog_id`，而 `program` 又能沿 `ws_id → workspace.uid` 回到一个用户。写入前必须校验收敛（`divergence.uid == program → workspace.uid`），否则会出现「分歧记录归属 A、其程序归属 B」的跨链矛盾。这条校验放在 `DiffService::startDiff()` 落库前（**在事务之外**），失败即拒绝写入并返回归属错误。

> 不采用「为每个用户建独立 schema」：云端用户数不可预知，schema 数量会失控；本地单用户形态下完全多余。同一模式 + 归属谓词是两种形态都能用的唯一写法。

#### 6.4.5 配额统计的实现

| 配额维度 | 来源 | 实时占用（`Usage`）的求法 |
| --- | --- | --- |
| 并发会话数 | `user.quota_sessions` | `SELECT COUNT(*) FROM session WHERE uid=? AND revoked=0 AND expires_at > ?` |
| 单次指令条数 | `user.quota_insns` | **不查库**——请求参数 `n` 与 `user.quota_insns` 直接比较 |
| 单会话内存 | `user.quota_mem_mb` | **不查库**——由内核运行期与分配器统计给出 |
| 工作区占用 | —（不限量，仅展示） | `sumWorkspace(uid)`：工作区数 + `SUM(LENGTH(image))` |

> **占用是「算出来」而不是「记下来」的**：不设 `usage` 计数列，避免每次执行都 `UPDATE` 一行形成热点行。代价是每次配额检查多一次聚合查询，但该表规模是「一个用户几十行」，代价可忽略。

#### 6.4.6 删除策略

| 数据 | 策略 | 语句 |
| --- | --- | --- |
| 会话 | **软删除 + 定期物理清理**：登出置 `revoked=1` 保留审计；到期回收直接删 | `UPDATE … SET revoked=1` / `DELETE FROM session WHERE expires_at < ?` |
| 工作区 | 硬删除，级联 `program` / `test_suite`（→ `test_case` / `test_report` → `case_result`） | `DELETE FROM workspace WHERE ws_id=? AND uid=?` |
| 程序 | 硬删除；**若被 `test_case` / `divergence` 引用则 RESTRICT 报错** | `DELETE FROM program WHERE prog_id=?` |
| 用例集 | 硬删除，级联用例与报告 | `DELETE FROM test_suite WHERE suite_id=?` |
| 报告 / 失败现场 | 硬删除（随用例集级联）；**已产生的报告不允许单独修改或删除** | — |
| 分歧记录 | 硬删除（随程序级联）；`tag` / `note` 可改，记录本身不可改 | — |
| 断点 | 硬删除 | `DELETE FROM breakpoint WHERE bp_id=?` |
| ISA 元数据 | **不删除**：被 `suite_isa` / `divergence` 引用时 RESTRICT；卸载 ISA 只是切到另一套 | — |
| 用户 | **不提供删除**：停用即 `UPDATE user SET status=0` | — |

> 「已产生的报告不可改不可删」与「分歧记录不可改」是**审计性**要求：报告是「当时确实这么跑过」的证据，允许改写会让报告失去意义（FR-6.3 的可回溯、FR-7.4 的归因复用都建立在不可篡改之上）。

#### 6.4.7 校验分层

| 层 | 校验内容 | 落点 |
| --- | --- | --- |
| **应用层（服务）** | 归属校验、配额校验、期望态与 `judge_mode` 的语义一致、映像合法性、ISA 描述完备性 | `SessionService` / `WorkspaceService` / `LoadService` / `QuotaGuard` / `IsaValidator` |
| **约束层（DB）** | 主键、唯一、外键、`CHECK`、`NOT NULL` | 6.3.5 的建表约束 |
| **驱动层** | 类型与长度（超长、BLOB 超限）、参数个数、占位符 | `PgDriver` / `SqliteDriver` |

**分层原则**：应用层给出**可读的错误信息**（「工作区不属于当前用户」「剩余额度不足」），DB 层给出**不可绕过的兜底**（即使服务层写错了，也插不进非法数据）。二者不是二选一。

### 7.3 逐子系统构件设计

#### 7.3.1 SS-1 模拟执行内核子系统

**职责**：执行取指—译码—执行—写回循环，维护架构状态，记录执行轨迹，判定终止与运行期异常。**链接依赖为零**，可独立编译为 `libisa_core` 并单独做单元测试。

| 方向 | 接口 | 主要操作 | 使用者 | 稳定性 |

**两条硬性对象生命周期约束**

1. **业务代码禁止直接 `new EmulatorCore`**：一律经 `CoreFactory`；`CoreFactory` 的参数（是否挂轨迹）来自配置。这样「轨迹开关」只有一个来源，NFR-Q1 的「关断换吞吐」不需要改动任何服务代码。
2. **`RunContext` 是一次性对象**：`drop()` 之后进入不可达状态，`Running` 无法直达 `Disposed`（见 `状态图-RunContext.svg`）。批量执行中共用一个 `RunContext` 会立刻使 NFR-Q2 失效——因此 `TestService::executeCase()` 的第一件事就是构造新的 `RunContext`。

**`Persistence` 的双驱动设计（DD-6）**：同一套 DAO 接口，云端绑定 PostgreSQL 驱动、本地绑定 SQLite 驱动。驱动差异全部收敛在 `DbDriver` 抽象之下，`Persistence` 及其使用者看到的是同一套 17 个方法与同一套方言无关的 DML；DDL 分两份、`Dialect` 枚举只影响自增主键与分页的取值方式。

**职责**：对外提供 HTTP 与 WebSocket 接口，承载鉴权与资源限额；并作为**组合根**装配全部单例构件。

**装配次序即依赖次序**（见 `活动图-服务端构件装配与启动.svg`）：驱动 → 模式迁移 → ISA 注册表 → 内核工厂与限额 → 服务 → 网关 → 监听并自检。任一环节失败都以分段退出码结束进程，不进入半可用状态。

### 7.4 构件级数据设计（所有权与并发）

数据设计解决的是**落库**，本节解决的是**运行期数据的所有权与可见性**——这是并发正确性的前提。

| 构件 / 数据 | 内容 | 生命周期 | 所有权 | 并发可见性 |
| --- | --- | --- | --- | --- |
| `Persistence` | 连接池、驱动句柄、方言标识 | 进程级 | `Bootstrapper` 装配的单例 | 连接按线程借用，不在构件内共享 |
| `IsaRegistry` / `DecodeTable` | 已装载描述、当前译码表 | 进程级 | 单例 | **只读共享**；切换激活 ISA 时以 `shared_ptr` 原子替换，正在执行的内核持旧表引用，引用计数保证不悬空 |
| `CoreFactory` | 创建参数（轨迹开关） | 进程级 | 单例 | 只读 |
| `QuotaGuard` | 限额配置 + 实时占用 | 进程级（占用按用户聚合） | 单例 | **需同步**：占用计数用原子量，与数据库对齐按周期进行 |
| `AuthFilter` | 票据缓存（token → uid + 有效期） | 进程级 | 单例 | **需同步**（读写锁）；过期条目惰性清理 + 定时清理 |
| `ProcessRunner` | 无状态 | —— | 无 | 每次调用独立 |
| `RunContext` | 内核指针、轨迹、起始时间、剩余限额 | **单次执行** | `TestService` / `DebugService` 每用例构造并销毁 | **线程封闭**：一个 `RunContext` 只在一个线程内使用 |
| `EmulatorCore` / `ArchState` / `Trace` / `TrapUnit` | 执行体与现场 | 与 `RunContext` 同生命周期 | 由 `RunContext` 拥有（经 `CoreFactory` 创建） | 线程封闭 |
| `ProgramImage` | 只读映像 | 一次执行 | `LoadService` 创建，`RunContext` 持引用 | 只读共享：**多用例可安全复用同一映像** |
| `BreakpointTable` | 会话级断点 | 调试会话 | `DebugService` 按会话持有 | **需同步**（界面线程登记 + 执行线程查询） |
| `TestReport` | 报告内存副本 | 生成 → 落库 → 释放 | `TestService` | 构建后不可变 |
| `StepResult` | 单步结果值对象 | 单步 | 调用方 | 即用即弃，值语义 |
| 前端 `StateStore` | 页面状态 | 页面级 | 视图层 | 浏览器事件循环单线程 |

**并发模型小结（三条结论）**

1. 服务端采用「**无状态单例服务 + 线程封闭的执行上下文**」：7 个服务构件都是无状态的，所有请求态都在 `RunContext` 里。因此真正需要并发保护的对象只有两个——`QuotaGuard` 的占用计数与 `AuthFilter` 的票据缓存。
2. 一次长任务（批量测试、对拍）占用一个工作线程直到结束，其内部的用例**串行执行**。选择串行而非并行：解释器的单线程吞吐已足以在 30 秒预算内跑完 10⁷ 条指令，而串行让 NFR-Q2 的隔离判定变得可验证（每个用例的 `RunContext` 严格前后相继，不存在交叉污染的可能）。
3. `ProgramImage` 是唯一被跨用例共享的可变长度数据，因此它的只读性是**类型级的**（`const ProgramImage*`），不是约定级的。

### 7.5 构件状态与协作

绝大多数构件是无状态或纯数据的，只有两个构件有值得建模的状态机：

| 构件 | 状态模型 | 图件 |
| --- | --- | --- |
| `DebugService` | 调试会话级状态机：`Idle → Loaded → Ready → Running ⇄ Paused → Finished / Faulted`，终止态可经 `reset()` 回到 `Idle` | `状态图-DebugService构件.svg` |
| `EmulatorCore`（类对象层） | 执行体级状态机：`Uninitialized → Ready → Running ⇄ Paused → Terminated / Faulted` | `状态图-EmulatorCore.svg` |

两张状态图是**叠加**关系而非重复：构件状态描述「调试会话对外可见处于什么阶段」（决定哪些请求合法），内核状态描述「执行体内部处于什么阶段」（决定 `step()` 的前置条件）。例如「会话处于 Paused」与「内核处于 Running」是不可能的组合——`DebugService` 在 `pause()` 未返回前不改变会话状态。

14 个用例的构件级协作已由 `UD-01` ~ `UD-14` 顺序图给出，本阶段不重复绘制，只补两张「构件视角」的图：`活动图-服务端构件装配与启动.svg`（**静态装配**：构件之间的创建与注入次序）与 `构件图-子系统接口总览.svg`（**动态协作的依赖前提**：谁可以向谁发消息）。

| # | 发现问题 | 处置 | 编号 |
| --- | --- | --- | --- |
| 1 | **内核与 ISA 抽象之间存在双向依赖**：`EmulatorCore` 需要 `DecodeTable`（SS-2），而体系结构的分层表又把 SS-2 画在 SS-1 之上；若让 `libisa_core` 链接 `libisa_isa`，内核就会间接依赖 JSON 库，与 DD-7 和 NFR-I2 正面冲突 | 引入 `IDecodeTable`（定义在 SS-1 的公共头）与执行层值类型 `InsnSemantic`，把依赖反转；`DecodeTable` 继承并实现该接口。链接方向变成 `libisa_isa → libisa_core`，**单向无环** | **DD-11** |
| 2 | **`ICoreService` 粒度太粗**：把「执行、状态读取、创建、装载、断点注入」放在同一接口里，而五个使用者没有一个需要全部操作；且 `loadImage()` 与 `init(prog, entryPC, sp)` 表达同一件事 | 按角色拆为 `ICoreService`（执行 + 状态读取）、`ICoreFactory`（创建）、`IBreakpointSink`（断点注入）；删去 `loadImage()` | **DD-12** |
| 3 | **配额被内核调用点复用会破坏分层**：把「内核调用点」列为 `IQuotaGuard` 的使用者，即内核要反向依赖 SS-6 | 限额只在 `HttpGateway` 一处前置检查；指令条数上限作为 `RunSpec.maxSteps` **参数**传给内核，内核只做被动计数并在达限时按终止处理，它不知道「配额」这个概念 | **DD-13** |
| 4 | **缺少唯一装配点**：双形态差异（驱动、限额开关、端口、轨迹默认值）散落在各服务的构造函数里，没有任何一处能完整回答「这个实例被配置成了什么形态」 | 新增组合根构件 `Bootstrapper`（SS-6），全部单例在此装配；业务代码中不允许出现单例的 `new` | **DD-14** |

**四条优化各自的收益**

| 编号 | 收益 | 可验证方式 |
| --- | --- | --- |
| DD-11 | 内核链接依赖归零，`core_only` 目标可在无网络、无数据库环境下编译并跑通 doctest；同时内核不再出现「描述文件」概念，`funct7` 与掩码的知识被彻底隔离在 SS-2 | 构建断言 A / D |
| DD-12 | 接口隔离：`TestService` 只依赖 `ICoreFactory`，看不到断点能力；`DebugService` 只依赖 `ICoreService` + `IBreakpointSink`，看不到批量创建能力。冻结级接口表面积从 10 个操作降到 6 个 | 逐使用者核对可见操作集（7.3 各表「需求接口」列） |
| DD-13 | 内核保持零外部依赖，分层单向；同时「指令条数上限」从横切能力变成普通参数，测试可直接传入小上限做快速用例 | `RunSpec.maxSteps = 0` 表示不限额 |
| DD-14 | 装配过程可单点审计、可单点替换；本地形态的「关闭限额」从「每个服务各自判断」变成「组合根少调一次 `enable()`」 | `活动图-服务端构件装配与启动.svg` |

**故意不做的优化（记入设计决策）**

- **不把 `Persistence` 拆成 5 个 DAO**：17 个方法的接口确实偏大，但当前只有 4 个使用者，且拆分会引入 5 个新的单例装配项。判断是「收益不足以抵消装配复杂度」，记为演进方向而非本次决策。
- **不让用例并行执行**：见 7.4 并发结论 2。
- **不引入消息队列 / 异步任务**：NFR-Q1 的本地 100 ms 单步响应要求最短链路，异步化会把延迟变成不可预测的值。

## 8 设计模式应用

### 8.1 采用的模式

| # | 模式 | 类型 | 应用位置 | 采用理由 | 对应质量属性 |
| --- | --- | --- | --- | --- | --- |
| 1 | **模板方法** | 行为型 | `ServiceBase::withTransaction(fn)`、`# log(fmt, …)` | 事务的「提交 / 回滚 / 异常上抛」骨架在 7 个服务中完全相同，只有中间的业务步骤不同。模板方法把易错的 `BEGIN`/`COMMIT`/`ROLLBACK` 骨架收敛到一处，业务代码**不可能漏掉回滚** | 可靠性、可修改性 |
| 2 | **工厂方法 / 抽象工厂** | 创建型 | `ICoreFactory` / `CoreFactory::create(traceEnabled)` | NFR-Q2 要求内核按用例创建，必须有一个集中的创建点。用工厂把「创建参数（是否挂轨迹）」与「使用」分离，也使将来换成进程隔离时只需改这一处 | 可靠性、可扩展性 |
| 3 | **桥接（Bridge）** | 结构型 | `IDecodeTable` + `InsnSemantic` + `OpClass` | 它把两个独立变化的维度分开：**执行机制**（内核实现在变）与**指令集定义**（描述文件在变）。这是 FR-1.1「描述驱动、新增 ISA 不改内核」的直接实现，也是 DD-11 依赖倒置的载体 | 可扩展性、可测试性 |
| 4 | **适配器（Adapter）** | 结构型 | `ToolchainAdapter` / `RefSimAdapter` + 端口 `IToolchainPort` / `IRefSimPort` | 外部工具链与 Spike 的接口最易变化，且不在本项目控制之下。端口—适配器把变化隔离在两个构件内，接口变化不外溢到内核与业务逻辑 | 可修改性、可靠性（降级路径） |
| 5 | **外观（Facade）** | 结构型 | `IsaRegistry` 作为 ISA 子域外观；`HttpGateway` 作为服务层的统一入口 | `IsaRegistry::install()` 把 `parse → validate → build` 三步包装成一次调用，调用方不需要知道内部三步；`HttpGateway::handle()` 把「鉴权 → 限额 → 分发 → 封装」包装成一个入口 | 简练、可维护 |
| 6 | **备忘录（Memento）** | 行为型 | `ArchState::snapshot() / restore()` + `Trace::snapshotAt(no)` | UC-07「回退执行历史」要求把架构状态恢复到任意历史步。备忘录把「状态的保存」与「状态的恢复」交给状态持有者自己，调用方（`DebugService`）不接触内部结构 | 功能正确性（FR-4.4） |
| 7 | **观察者 / 发布—订阅** | 行为型 | `StatusChannel`（后端）→ `StateStore`（前端）→ 各视图 | 执行状态的增量推送是「一对多」依赖：一次执行会同时影响寄存器、内存、反汇编、轨迹四个视图。用观察者把「数据变化」与「界面刷新」解耦，视图之间**无直接关系**（5.3 关系 #44） | 可修改性、易用性（NFR-Q3） |
| 8 | **策略（Strategy）** | 行为型 | `DbDriver`（`PgDriver` / `SqliteDriver`）；`DiffScope`（比对子集） | 数据库方言与比对口径都是「同一接口、多种可替换算法」。换驱动不触发任何 DML 修改；改比对子集不触碰 `CompareEngine` 代码 | 可扩展性、可移植性（T8） |
| 9 | **组合根 + 受管单例** | 创建型（变体） | `Bootstrapper` 装配 `Persistence` / `CoreFactory` / 7 个服务 / `QuotaGuard` 等单例 | 双形态差异（驱动、限额、端口、轨迹默认值）必须**单点决定**。这里刻意采用「组合根 + 构造函数注入」而非 GoF 单例，理由见 8.2 | 可测试性、可修改性 |
| 10 | **模型—视图—控制器（MVC）** | 架构型 | SS-7 前端：视图类 + `StateStore`（模型）+ 后端 `*Service`（控制器） | 界面与业务分离，前端不持有业务状态；视图随路由销毁不损失任何数据 | 可修改性、可移植性 |
| 11 | **管道—过滤器（Pipes and Filters）** | 架构型 | `EmulatorCore::step()` 内部的取指 / 译码 / 执行 / 写回四级私有单元 | 四级职责单一、可分别单元测试；「执行」不写状态、「写回」才写状态，这个切分本身就让 trap 判定有明确的插入点 | 可测试性、可维护性 |

### 8.2 刻意不采用的模式

| 模式 | 不采用的理由 |
| --- | --- |
| **GoF 单例（`getInstance()` 静态方法）** | 静态单例把依赖藏在实现里，单元测试无法替换（无法注入假 DAO），且装配顺序不可审计。改用 `Bootstrapper` + 构造函数注入：实例仍是进程唯一，但**可见、可替换、可审计** |
| **观察者用于服务之间** | 服务之间的调用关系是确定的、需要返回值的（如 `TestService → CompareEngine` 要拿到 `Verdict`）。事件式的服务间通信会把调用链变成隐式的，破坏 7.3 的依赖表的可核查性。观察者只用在「一次变化广播给多个视图」这一处 |
| **访问者（Visitor）** | 曾考虑用于「指令语义的多种处理」（执行 / 反汇编 / 校验）。但内核侧的语义处理只有"执行"一种，反汇编走描述层的字符串，校验在装载期完成——引入访问者会为一个不存在的需求付复杂度 |
| **代理（Proxy）用于内核隔离** | 若用代理包装 `EmulatorCore` 来记账/限流，就会把 SS-6 的横切关注点重新塞回内核调用链，与 DD-13 的结论相反。正确做法是把限额前置到 `HttpGateway`，把上限作为参数传入 |
| **状态（State）模式用于内核** | `CoreState` 迁移点少（6 个状态、7 条迁移）且迁移条件简单，用 `switch` 表达比引入状态类更直观。状态图本身仍保留（`状态图-EmulatorCore.svg`），服务于正确性审查而非实现 |
| **建造者（Builder）用于复杂对象** | 系统内最复杂的构造是 `DecodeTable`（由 `IsaSpec` 编译而来），但它只有一个构造参数、一次成型，工厂方法 `build(spec)` 已足够 |

### 8.3 模式与质量属性的对应

| 质量属性 | 主要依赖的模式 | 说明 |
| --- | --- | --- |
| 可扩展性（NFR-I1） | 桥接、适配器 | 新增 ISA = 新增描述文件；更换参考模拟器 = 实现一个端口 |
| 可测试性（NFR-I2） | 组合根、工厂、管道—过滤器 | 内核零依赖可独立编译；服务可注入假 `IStore` |
| 可靠性（NFR-Q2、NFR-Q5） | 模板方法、工厂、适配器 | 事务骨架单点；每用例独立内核；降级路径明确 |
| 可修改性 | 外观、策略、观察者 | 三步装配封装在 `install()`；换驱动不改 DML；视图刷新与数据源解耦 |
| 性能（NFR-Q1） | 管道—过滤器（四级分解无虚函数调用） | 单步链路上没有虚调用、没有异步、没有锁 |
| 部署形态对等（T8） | 策略 + 组合根 | 两形态差异只体现在驱动选择与四个开关上 |
