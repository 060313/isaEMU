## 一、持久化对象判定

### 1.1 判定口径

类设计共给出 **51 个类**（42 个设计类 + 8 个持久化实体类 + 本阶段首次显式化的 `Breakpoint`，另有 6 个接口）。其中**只有 12 个类的实例需要跨进程生命周期存活**，其余 **39 个不需要**。判据有两条，且必须同时满足：

1. **需求要求它跨会话存在**——进程重启后用户仍能看到它（FR-9.3 保存与加载、FR-9.4 账号会话、FR-9.5 隔离与配额、FR-6.3 报告回溯、FR-7.4 归因复用、FR-1.1 ISA 元数据、FR-4.2 断点）；
2. **它没有更便宜的载体**——若能从别的持久数据推导出来，就不落库（如 `Usage` 是聚合查询的结果，不建表；`StepResult` 是执行的即时产物，不落库）。

按这两条判据，**39 个不持久化的类**见下表（按类型分组，共 7 组）：

| 组 | 类（个数） | 不持久化的理由 |
| --- | --- | --- |
| 内核运行时状态（7） | `EmulatorCore`、`ArchState`、`Trace`、`TrapUnit`、`StepResult`、`RunContext`、`ProgramImage` | 生命周期与一次执行绑定（`RunContext` 是**一次性对象**）；需要留存的是它们的**快照**，而快照已由 `divergence` / `case_result` 以 JSON 承载。`ProgramImage` 在库中的对应物是 `program` 表的 `image`/`base`/`entry`/`sp` 四列 |
| ISA 内存结构（5） | `IsaSpec`、`IsaValidator`、`DecodeTable`、`IsaRegistry`、`InsnDef` | 由描述文件（`isa_meta.path`）**可重建**，落库只会造成「库与文件不一致」；落库的只有元数据 |
| 比对支撑（2） | `CompareEngine`、`DiffScope` | 无状态算法与比对口径（口径随 `divergence.scope_json` 落库） |
| 外部适配（3） | `ToolchainAdapter`、`RefSimAdapter`、`ProcessRunner` | 只持有路径、参数与超时等配置 |
| 领域服务与工厂（10） | `ServiceBase`、`CoreFactory`、`SessionService`、`WorkspaceService`、`LoadService`、`DebugService`、`TestService`、`DiffService`、`Persistence`、`BreakpointTable` | 无状态或只有运行期索引；`BreakpointTable` 是内存索引（本身体现在 `breakpoint` 表），其 `m_nextId` 亦可由库中最大值恢复 |
| 集成 API（4） | `HttpGateway`、`AuthFilter`、`QuotaGuard`、`StatusChannel` | 前两者是请求管道；`AuthFilter.m_tokens` / `StatusChannel.m_conns` 是**进程内索引与连接句柄**，`QuotaGuard.m_limits` 是配置 |
| Web 前端（8） | `HttpApiClient`、`StateStore`、`DebugView`、`TestView`、`DiffView`、`LoadView`、`IsaView`、`AdminViews` | 前端状态随页面销毁，持久化的是服务端数据而非视图状态 |

## 二、存储机制选择

### 2.1 关系数据库（而非数据文件）

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| **关系数据库** | **采用** | 12 张表之间存在 8 条 1:n 与 1 条 n:m，外键完整性由 DB 强制；FR-9.5 的「按用户统计资源占用」本质是聚合查询，用 SQL 一句可完成；并发写入有成熟的事务与锁语义 |
| 自定义二进制 / JSON 文件 | 不采用 | 12 张表的关联与聚合要手写，且无事务；FR-9.5 的多用户隔离会退化成"自己实现一遍 DB" |
| 文档数据库 | 不采用 | 本设计的关系是强结构化的（用例集 → 用例 → 报告 → 结果），文档模型反而要手工维护跨文档一致性 |

这与 SAD 5.12 的 **DD-6（PostgreSQL 云端 / SQLite 本地 双驱动）** 一致：**同一套关系模式，两种部署形态只换驱动**。

### 2.2 双驱动的分工

| 形态 | 驱动 | 适配的场景 | 关键约束 |
| --- | --- | --- | --- |
| 云端 | PostgreSQL 14+ | 多用户并发读写、配额聚合统计、跨容器持久卷 | 需要连接池；DDL 用 `GENERATED ... AS IDENTITY`；二进制用 `BYTEA` |
| 本地 | SQLite 3.35+ | 单机单用户、零配置、单文件 `local.db` | 单写者模型 → 开 `PRAGMA journal_mode=WAL` 与 `busy_timeout`；DDL 用 `INTEGER PRIMARY KEY AUTOINCREMENT`；二进制用 `BLOB` |

**为什么必须双驱动而不是统一 SQLite**：SAD 5.12 已裁定——纯 SQLite 在云端并发写入与配额统计上不可靠。反过来，把 PostgreSQL 塞进本地部署会让「单可执行文件、零配置」这条目标（T8、FR-9.2）失效。差异被压缩到 `DbDriver` 一个接口的两个实现里。

### 2.3 差异收敛清单（保证一套 DML 跑两形态）

| 差异点 | PostgreSQL | SQLite | 收敛方式 |
| --- | --- | --- | --- |
| 自增主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `INTEGER PRIMARY KEY AUTOINCREMENT` | **仅 DDL 分两份**，DML 不感知 |
| 参数占位符 | `$1, $2 …` | `?` | 驱动层按方言重写；`Persistence` 只传位置参数列表 |
| 布尔 | `BOOLEAN` | 无 → `INTEGER 0/1` | 驱动层映射 |
| 时间 | `TIMESTAMPTZ` | `TEXT` / `INTEGER` | **统一用 `BIGINT`（UTC 毫秒）**，应用层换算，彻底消除方言差异 |
| 二进制 | `BYTEA` | `BLOB` | 驱动层映射 |
| JSON | `JSONB`（可选） | `TEXT` | **统一用 `TEXT`**，序列化在应用层；`JSONB` 仅作为云端可选优化，不进默认 DDL |
| UPSERT | `ON CONFLICT (…) DO UPDATE SET …` | 同语法（3.24+） | **DML 只有一套** |
| 大小写 | 标识符折叠为小写 | 不折叠 | 全部表名列名使用小写下划线，不加引号 |
| 空串与 NULL | 区分 | 区分 | 允许为空的文本列显式写 `NULL`，不用空串代替 |

**不使用任何 DB 专有特性**：无存储过程、无触发器、无自定义函数、无物化视图、无共享序列、无 `RETURNING` 之外的扩展语法。这不是能力不足，而是「双形态功能对等」的结构性前提。

**与类设计的 8 个实体类对照**：`user` / `session` / `workspace` / `program` / `test_suite` / `test_case` / `case_result` / `isa_meta` 八张表与类设计 §3.7 的 8 个数据实体类**一一对应**。另外 4 张表是本次数据设计补充的：

| 补充表 | 为什么类设计里没有它 |
| --- | --- |
| `test_report` | `CaseResult.reportId` 是外键，**没有报告表外键就无处可指**；类设计里 `TestReport` 既是设计类（SS-5，含 `summarize()` 行为）又是持久实体，本阶段把它拆成「行为在 `TestService`、数据在 `test_report`」 |
| `divergence` | `Divergence` 在类设计里是 SS-3 的设计类（含 `m_id` 落库主键），本阶段补齐它的表结构 |
| `breakpoint` | 类设计 §3.5 只写了 `BreakpointTable.m_items : map<BpId, Breakpoint>`，`Breakpoint` 值类型未单列 |
| `suite_isa` | `TestSuite n:m IsaMeta` 在类设计 §2.2 已点出「需新增交叉表」，本阶段落地 |

### 3.2 逐表字段定义

> 「键」列：PK 主键、FK 外键、PK/FK 复合主键且同时是外键、UQ 唯一约束。所有表隐式带 `NOT NULL`（除非标 *可空*）。

#### 3.2.1 账号域

**`user` 用户**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `uid` | BIGINT | 自增主键 |
| UQ | `name` | VARCHAR(64) | 登录名，唯一 |
| | `pwd_hash` | VARCHAR(128) *可空* | 加盐口令散列；**本地匿名模式为 NULL**（FR-9.2） |
| | `role` | SMALLINT | 0 = User，1 = Admin（`Role`，UC-14 管理端靠此过滤） |
| | `quota_sessions` | INT | 并发会话数上限（NFR-Q5） |
| | `quota_insns` | BIGINT | 单次请求指令条数上限 |
| | `quota_mem_mb` | INT | 单会话内存上限 |
| | `status` | SMALLINT | 0 = Suspended，1 = Active（`UserStatus`） |
| | `created_at` | BIGINT | UTC 毫秒 |

> **三个配额字段直接摊在 `user` 表上，而不是单开 `quota` 表**：`Quota` 在类设计里是与 `User` **1:1 的组合**（`User.quota`），1:1 关系的最优落点就是同表同列——单开表会引入一次永远必需的 JOIN。

**`session` 登录会话**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `token` | VARCHAR(64) | 会话令牌，**直接作主键**（鉴权时必查，免二次索引） |
| FK | `uid` | BIGINT | → `user.uid`，`ON DELETE CASCADE` |
| | `expires_at` | BIGINT | 到期时间（空闲会话回收依据，NFR-Q5） |
| | `revoked` | BOOLEAN | 主动登出置 1（软删除，保留审计） |
| | `created_at` | BIGINT | — |

#### 3.2.2 工作区域

**`workspace` 工作区**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `ws_id` | BIGINT | — |
| FK | `uid` | BIGINT | → `user.uid`，`ON DELETE CASCADE`；**多用户隔离的第一道外键** |
| UQ | (`uid`, `name`) | — | 同一用户下工作区名唯一；不同用户可同名 |
| | `name` | VARCHAR(64) | — |
| | `created_at` / `updated_at` | BIGINT | — |

**`program` 程序与映像**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `prog_id` | BIGINT | — |
| FK | `ws_id` | BIGINT | → `workspace.ws_id`，`ON DELETE CASCADE` |
| UQ | (`ws_id`, `name`) | — | — |
| | `name` | VARCHAR(128) | 程序名（汇编源文件名或用户命名） |
| | `base_addr` / `entry_addr` / `sp_init` | BIGINT | 装入基址 / 入口 / 初始 SP |
| | `image` | BLOB | **机器码映像本体**（FR-9.3 保存的就是它） |
| | `created_at` | BIGINT | — |

> **`base_addr` 等地址字段用 `BIGINT` 而非 `INT`**：类设计里它们是 `uint32`，上界 4294967295 **超过**有符号 `INT` 的上限 2147483647。用 `INT` 会让高位地址（如 `0x80000000`）插入即溢出报错——这是本阶段最容易埋下、又最难在测试中发现的坑。

#### 3.2.3 测试域

**`test_suite` 用例集**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `suite_id` | BIGINT | — |
| FK | `ws_id` | BIGINT | → `workspace.ws_id`，`ON DELETE CASCADE` |
| UQ | (`ws_id`, `name`) | — | — |
| | `name` | VARCHAR(128) | — |
| | `tags` | VARCHAR(512) *可空* | 逗号分隔的标签串；**不做标签表**，因为需求中标签只用于展示（FR-6.1） |
| | `updated_at` | BIGINT | — |

**`suite_isa` 用例集–ISA 交叉表（n:m 落点）**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK/FK | `suite_id` | BIGINT | → `test_suite.suite_id`，`ON DELETE CASCADE` |
| PK/FK | `spec_id` | BIGINT | → `isa_meta.spec_id`，`ON DELETE RESTRICT` |
| | `is_default` | BOOLEAN | 该用例集的默认 ISA；**同一 suite 至多一行为 1**（应用层保证 + 部分唯一索引） |

> **n:m 必须新增交叉表**：`TestSuite` 与 `IsaMeta` 的 n:m 关系无法在任何一端用外键表达。交叉表存两端外键构成联合主键，天然去重（同一个用例集不会重复挂同一份 ISA）。附加的 `is_default` 是需求要求的「每个用例集指定其运行 ISA」的落点（FR-1.3）。

**`test_case` 测试用例**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `case_id` | BIGINT | — |
| FK | `suite_id` | BIGINT | → `test_suite.suite_id`，`ON DELETE CASCADE` |
| FK | `prog_id` | BIGINT | → `program.prog_id`，**`ON DELETE RESTRICT`** |
| | `name` | VARCHAR(128) *可空* | — |
| | `judge_mode` | SMALLINT | 0 = FinalSnapshot，1 = CommitLog（`JudgeMode`，FR-6.5 两模式） |
| | `insn_limit` | BIGINT | 0 = 不限；否则为该用例的指令条数上限（NFR-Q5） |
| | `expect_final` | TEXT *可空* | `judge_mode = 0` 时非空：`Snapshot` 的 JSON |
| | `expect_commits` | TEXT *可空* | `judge_mode = 1` 时非空：`StateRecord[]` 的 JSON |

约束：

- `CHECK ((judge_mode = 0 AND expect_final IS NOT NULL) OR (judge_mode = 1 AND expect_commits IS NOT NULL))` —— **两种期望态互斥且必居其一**，把 FR-6.5 的「两者都支持」从口头约定变成 DB 层约束；
- `prog_id` 取 `RESTRICT` 而非 `CASCADE`：删掉一个程序映像时，若仍有用例引用它，**必须报错而不是静默删除用例**，否则用户会莫名其妙丢掉测试用例。

**`test_report` 执行报告**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK | `report_id` | BIGINT | — |
| FK | `suite_id` | BIGINT | → `test_suite.suite_id`，`ON DELETE CASCADE` |
| | `judge_mode` | SMALLINT | 本次执行采用的判定模式 |
| | `total` | INT | 用例总数 |
| | `passed` | INT | 通过数 |
| | `started_at` / `finished_at` | BIGINT | `finished_at` 可空 = 执行中断（NFR-Q2 异常隔离下仍留痕） |
| | `triggered_by` | VARCHAR(64) *可空* | 触发者标识（UID 或 CI 客户端），对应 FR-6.4 的 CI 驱动 |

约束：`CHECK (passed <= total)`、`CHECK (passed >= 0)`。

> **报告是「只增不改」的**：每次执行新增一行，历史报告永久保留（FR-6.3 要求可回溯），因此不存在 UPDATE 冲突。这也让并发执行同一用例集无需互斥——两个请求各自写自己的报告行。

**`case_result` 失败现场**

| 键 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| PK/FK | `report_id` | BIGINT | → `test_report.report_id`，`ON DELETE CASCADE` |
| PK/FK | `case_id` | BIGINT | → `test_case.case_id`，`ON DELETE CASCADE` |
| | `verdict` | SMALLINT | 0 = Pass，1 = Fail，2 = Partial（`Verdict`） |
| | `snap` | TEXT *可空* | 失败现场 `Snapshot` 的 JSON |
| | `diff_step` | BIGINT *可空* | 首个差异步号 |
| | `diff_field` | VARCHAR(64) *可空* | 差异字段名 |
| | `ours_val` / `ref_val` | VARCHAR(64) *可空* | 双方取值（字符串化，便于直接展示） |

> **只存失败用例**：与类设计 §3.5「`m_failures` 仅存失败用例，通过的只计数」严格一致。1000 个用例全部通过时本表写 0 行，报告表只写 1 行——这是 NFR-Q1 吞吐指标在落库环节的直接体现。
>
> 复合主键 (`report_id`, `case_id`) 使「一个报告内一个用例只有一条结果」由 DB 保证，不用应用层去重。

#### 3.2.4 ISA 域与对拍域

**`isa_meta` ISA 描述元数据**

| 键 | 字段 | 类型 | 说明 |

> **本表全局共享、不带 `uid`**：ISA 描述是系统级资产而非用户数据（FR-1.1~FR-1.3 未要求用户各自上传私有 ISA）。若后续要支持私有 ISA，只需加一列 `uid`（可空 = 全局），不影响现有查询。

**`divergence` 对拍分歧**

| 键 | 字段 | 类型 | 说明 |

### 3.3 关系落点汇总

> 类设计 §2.2 给出 10 条持久化关系；本阶段落地时**新增 5 条**（标 ★），全部是外键可表达的关系。

| # | 关系 | 基数 | 落点 | 外键位置 |
| --- | --- | --- | --- | --- |
| 1 | `User` — `Session` | 1 : 0..n | `session.uid` | n 端 |
| 2 | `User` — `Workspace` | 1 : 0..n | `workspace.uid` | n 端 |
| 3 | `Workspace` — `ProgramRecord` | 1 : 0..n | `program.ws_id` | n 端 |
| 4 | `Workspace` — `TestSuite` | 1 : 0..n | `test_suite.ws_id` | n 端 |
| 5 | `TestSuite` — `TestCase` | 1 : 0..n | `test_case.suite_id` | n 端 |

| 7 | `TestSuite` — `TestReport` | 1 : 0..n | `test_report.suite_id` | n 端 |
| 8 | `TestReport` — `CaseResult` | 1 : 0..n | `case_result.report_id` | n 端 |
| 9 | `TestCase` — `CaseResult` | 1 : 0..n | `case_result.case_id` | n 端 |
| 10 | `TestSuite` — `IsaMeta` | **n : m** | **`suite_isa` 交叉表** | 交叉表两端 |

| 15 ★ | `ProgramRecord` — `Breakpoint` | 1 : 0..n | `breakpoint.prog_id` | n 端 |

**三条落点规律**（也是技能对数据设计的规定动作）：

1. **1:1 并入主表**：`User` — `Quota` 没有独立表，三个配额列直接进 `user`（1.2 注已说明）。
2. **1:n 外键建在 n 端**：上表 1~9、12~15 共 13 条 1:n 关系，外键一律建在子表；**子表恒为「多」的那一侧**（`session` 之于 `user`、`case_result` 之于 `test_report`）。
3. **n:m 新增交叉表**：全系统只有 `TestSuite` — `IsaMeta` 一条 n:m，落在 `suite_isa`。

### 3.5 约束设计（DB 层兜底）

| 约束类型 | 实例 | 意图 |
| --- | --- | --- |
| 主键 | 12 张表全部有主键（其中 2 张为复合主键） | 行唯一标识 |
| 唯一 | `user.name`、`session.token`（主键兼任）、(`uid`,`name`)、(`ws_id`,`name`)×2、(`name`,`version`)、(`prog_id`,`addr`) | 业务唯一性，把「重名/重复登记」挡在 DB 层 |
| 外键 + `ON DELETE` | 15 条（3.3 表） | 完整性；`CASCADE` 用于「子数据随父数据无意义」，`RESTRICT` 用于「删父会静默毁掉用户资产」 |
| `CHECK` | `test_case` 期望态互斥；`test_report.passed <= total`；`passed >= 0` | 领域不变式 |
| 枚举值域 `CHECK` | `role ∈ {0,1}`、`status ∈ {0,1}`、`judge_mode ∈ {0,1}`、`verdict ∈ {0,1,2}`、`tag ∈ {0..3}` | 防止写入未定义枚举 |
| `NOT NULL` | 除标注「可空」的列外全部非空 | 避免应用层到处判空 |

> **枚举值域用 `CHECK` 而不是 DB 原生 `ENUM`**：PostgreSQL 的原生枚举类型在 SQLite 里不存在，会破坏 2.3 的差异收敛原则。用 `SMALLINT + CHECK` 两形态一致，且枚举值只在应用层有名字。

### 4.3 事务边界

| 事务 | 范围 | 隔离级别 | 理由 |
| --- | --- | --- | --- |
| 工作区保存（UC-12） | ④⑤⑥ | READ COMMITTED（两形态默认） | 四类 UPSERT 必须整体成功或整体失败，否则工作区会出现「程序有了、用例集没有」的半写状态 |
| 报告落库（UC-08） | ⑦⑧ | READ COMMITTED | 报告行与失败现场行必须同生共死 |
| 单条读 | 无显式事务 | 自动提交 | 读操作不显式开事务，避免长连接占用 |
| 会话创建 | 单语句 | 自动提交 | 无跨表约束 |

**事务模板方法**：`ServiceBase::withTransaction(fn)`（类设计 §4.1）——正常返回则 `COMMIT`，抛异常则 `ROLLBACK` 并继续上抛。所有跨表写操作都在这个模板里执行，**没有任何一处业务代码手写 BEGIN/COMMIT**，避免漏回滚。

### 4.4 多用户隔离的实现方式

**隔离不靠数据库权限，靠每条语句的归属谓词。** 具体三条规则：

1. **每个涉及用户数据的查询都带 `uid` 或 `ws_id` 条件**——`WHERE prog_id = ? AND uid = ?` 而非先查后判。`divergence` 表的读取即按此写法（4.1 表已标注）。
2. **归属链全程可追**：`uid → workspace → program / test_suite → test_case → test_report → case_result`。任何一张子表的行都能沿外键回到 `uid`，不存在「孤儿行」。
3. **写操作先验证归属再写**：UC-12 的第 ① 步（`SELECT uid FROM workspace …`）就是这条规则，校验不通过连事务都不开。

> 不采用「为每个用户建独立 schema」的方案：云端用户数不可预知，schema 数量会失控；本地单用户形态下更是完全多余。同一模式 + 归属谓词是两种形态都能用的唯一写法。

### 4.5 配额统计的实现

| 配额维度 | 来源（`Quota`） | 实时占用（`Usage`）的求法 |
| --- | --- | --- |
| 并发会话数 | `user.quota_sessions` | `SELECT COUNT(*) FROM session WHERE uid=? AND revoked=0 AND expires_at > ?` |
| 单次指令条数 | `user.quota_insns` | **不查库**——请求参数 `n` 与 `user.quota_insns` 直接比较 |
| 单会话内存 | `user.quota_mem_mb` | **不查库**——由内核运行期的 `m_insnLimit` 与分配器统计给出 |
| 工作区占用 | —（不限量，仅展示） | `sumWorkspace(uid)`：工作区数 + `SUM(LENGTH(image))` |

> **占用是「算出来」而不是「记下来」的**：不设 `usage` 计数列，避免每次执行都去 `UPDATE` 一行——那会在并发下形成热点行。代价是每次配额检查多一次聚合查询，但该表规模是「一个用户几十行」，代价可忽略。这一点在 `活动图-工作区保存落库.svg` 的第 ② 步可见。

### 4.6 删除策略

| 数据 | 策略 | 语句 |
| --- | --- | --- |
| 会话 | **软删除 + 定期物理清理**：登出置 `revoked=1` 保留审计；到期回收直接删 | `UPDATE … SET revoked=1` / `DELETE FROM session WHERE expires_at < ?` |
| 工作区 | 硬删除，级联 `program` / `test_suite`（→ `test_case` / `test_report` → `case_result`） | `DELETE FROM workspace WHERE ws_id=? AND uid=?` |
| 程序 | 硬删除；**若被 `test_case` / `divergence` 引用则 RESTRICT 报错** | `DELETE FROM program WHERE prog_id=?` |
| 用例集 | 硬删除，级联用例与报告 | `DELETE FROM test_suite WHERE suite_id=?` |
| 报告 / 失败现场 | 硬删除（随用例集级联）；已产生的报告不允许单独修改或删除 | — |
| 分歧记录 | 硬删除（随程序级联）；`tag` / `note` 可改，记录本身不可改 | — |
| 断点 | 硬删除 | `DELETE FROM breakpoint WHERE bp_id=?` |
| ISA 元数据 | **不删除**：被 `suite_isa` / `divergence` 引用时 RESTRICT；卸载 ISA 只是 `activate` 到另一套 | — |
| 用户 | **不提供删除**：停用即 `UPDATE user SET status=0`；`ON DELETE CASCADE` 仅为模式完整性保留 | — |

> 「已产生的报告不可改不可删」与「分歧记录不可改」是**审计性**要求：报告是「当时确实这么跑过」的证据，允许改写会让报告失去意义（FR-6.3 的可回溯、FR-7.4 的归因复用都建立在不可篡改之上）。

### 4.7 校验分层

| 层 | 校验内容 | 落点 |
| --- | --- | --- |
| **应用层（服务）** | 归属校验、配额校验、期望态与 `judge_mode` 的语义一致、映像合法性（`LoadService::checkImage`）、ISA 描述完备性（`IsaValidator::validate`） | `SessionService` / `WorkspaceService` / `LoadService` / `QuotaGuard` / `IsaValidator` |
| **约束层（DB）** | 主键、唯一、外键、`CHECK`、`NOT NULL` | 3.4 / 3.5 的建表约束 |
| **驱动层** | 类型与长度（`VARCHAR(n)` 超长、BLOB 超限）、参数个数、占位符 | `PgDriver` / `SqliteDriver` |

**分层原则**：应用层给出**可读的错误信息**（「工作区不属于当前用户」「剩余额度不足」），DB 层给出**不可绕过的兜底**（即使服务层写错了，也插不进非法数据）。二者不是二选一，任何一层缺失都会在某个用例上暴露。

## 五、数据访问层设计

### 5.1 结构（见 `类图-数据访问层.svg`）

```
6 个领域服务 / AuthFilter / QuotaGuard
        │ 仅依赖接口
        ▼
     IStore  «interface»            ← 契约稳定级（SAD 5.10）
        ▲ 实现
        │
   Persistence  «dao»  ──聚合──▶  DbDriver «interface»
        │                              ▲ 实现
        │ 依赖                          ├── PgDriver      （云端）
        ▼                              └── SqliteDriver  （本地）
   SchemaMigrator  ──依赖──▶ DbDriver
        │
        ▼
     DbConfig «struct»  （driver / connStr / poolSize / busyTimeoutMs）
```

**关键点**：`Persistence` 持有的是 `DbDriver*` 而不是 `PgDriver*` 或 `SqliteDriver*`。驱动在进程启动时按 `DbConfig.driver` 选定并注入，**发布后换部署形态不需要重新编译**。

### 5.2 本次数据设计新增的设计元素（6 个）

| 元素 | 构造型 | 职责 | 为什么必须新增 |
| --- | --- | --- | --- |
| `DbDriver` | «interface» | 连接、执行、查询、事务、方言标识 | 类设计只写到「`Persistence.m_driver : DbDriver` 由配置决定」，未定义这个抽象；没有它双驱动就只能靠 `#ifdef` |
| `PgDriver` | «driver» | PostgreSQL 实现 | 云端形态的落点 |
| `SqliteDriver` | «driver» | SQLite 实现 | 本地形态的落点 |
| `SchemaMigrator` | «component» | 建表与版本迁移 | 对应 SAD 6.5 的「数据库模式脚本」制品；两套方言 DDL 各一份 |
| `DbConfig` | «struct» | 驱动选择、连接串、池大小、超时 | 配置数据的载体，供组合根注入 |
| `Dialect` | 枚举 | `Pg` / `Sqlite` | 驱动自我标识与 DDL 分支的唯一依据 |

> `Conn`（连接 / 连接池句柄）与 `RowSet`（结果行集）是驱动接口的不透明类型，不进类图展开。

### 6.1 与类设计的差异（6 处，均已在文中说明）

| # | 差异 | 说明 |

| 1 | 新增 4 张表（`test_report` / `divergence` / `breakpoint` / `suite_isa`） | 前三张是类设计里「既是设计类又需落库」或「值类型未单列」的补齐，第四张是 n:m 的必然产物；见 3.1 表 |
