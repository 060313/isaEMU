### 1.3 可见范围策略

技能要求「尽可能缩小可见范围，遵循信息隐藏原则」。本设计采用**三档 + 一处例外**：

| 档位 | 适用范围 | 数量级 |
| --- | --- | --- |
| **public** | 类的构造与析构、对外契约方法（接口的实现方法、被其他子系统调用的方法） | 约 78% |
| **private** | 实现细节：管道各级、校验子检查、解析器内部函数、脏页标记等 | 约 22%（30 个方法） |
| **protected** | 仅 `ServiceBase` 的 `m_log` / `m_cfg` 与模板方法 `withTransaction()` | 2 属性 + 2 方法 |
| 例外 | 值对象（«struct»）成员全部 public | `StepResult`、`InsnDef`、`StateRecord` 及第五章的值类型 |

**三处需说明的判断**：

1. **类级可见范围全部为 public，不用 `friend` 也不做内部类。** 语言层面 C++ 的类默认可见性不构成封装边界（同一静态库内一律可互相引用），真正的边界由**构建脚本**强制：内核静态库 `libisa_core` 不链接任何网络 / JSON / 数据库库，跨库引用即链接失败（SAD 5.9）。这是把 NFR-I2 从「口头约定」变成「编译期约束」的落点。
2. **protected 缺省不用，是因为类间不存在泛化。** 分析阶段已裁定：用例图里四类用户对「注册用户」的泛化是**执行者层**的泛化，不得映射成类继承。全系统唯一的继承链是 6 个领域服务 → `ServiceBase`，protected 就落在这条链上。
3. **值对象成员公开是有意为之。** `StepResult` 这类对象没有不变式需要保护（拿到即读），若强行加 getter 只会让 `EmulatorCore::step()` 的返回值处理多出十几行样板。判据是「**有无需要维护的不变式**」，不是「数据还是行为」。

### 2.2 与持久化相关的关系（供第 6 章）

`User 1:0..n Session`、`User 1:0..n Workspace`、`Workspace 1:0..n ProgramRecord`、`Workspace 1:0..n TestSuite`、`TestSuite 1:0..n TestCase`、`TestCase 0..n:1 ProgramRecord`、`TestSuite 1:0..n TestReport`、`TestReport 1:0..n CaseResult`、**`TestSuite n:m IsaMeta`**、`Divergence 1:2 StateRecord`。详见 `类图-核心对象关系.svg`。其中 `n:m` 需新增交叉表，其余在 n 端加外键。

### 2.3 两处维持不变的结构判断

**第一，组合只有 2 处（按语义计共 8 条，集中在「生命周期一致」的对象上）。** 判据是「**被持有者的生命周期是否与持有者完全一致**」：`ArchState` / `Trace` / `TrapUnit` 随内核创建销毁（组合）；而 `ProgramImage` 由 `LoadService` 创建、可被工作区保存与重新装载，`BreakpointTable` 的生命周期与调试会话一致——都是可独立存在的关联，用组合会把后续的可测试性与回退能力写死。

**第二，`CompareEngine` 被 `TestService` 与 `DiffService` 同时依赖，在图上是可见的两条边。** 这条关系从分析阶段的 `CompareEngine` 独立类、SAD 阶段的 SS-3 独立子系统，一路保留到详细设计，是 FR-6.5「两种判定模式复用同一比对引擎」在三个层次上的同名落点。**它不许在设计阶段被合并进任一服务。**

## 六、对象的创建与销毁

| 对象 | 创建者 | 销毁者 | 生命周期 |
| --- | --- | --- | --- |
| `ArchState` / `Trace` / `TrapUnit` | `EmulatorCore` 构造 | `EmulatorCore` 析构 | 与内核一致（组合） |
| `EmulatorCore` | **仅 `CoreFactory::create()`** | `CoreFactory::destroy()` 或 `RunContext::drop()` | 按用例 / 按会话 |
| `ProgramImage` | `LoadService::loadProgram()` | 工作区控制器（随工作区释放） | 跨多次执行 |
| `DecodeTable` | `IsaRegistry::install()`（`DecodeTable::build()`） | `IsaRegistry` 析构 | 与激活 ISA 一致 |
| `IsaSpec` / `InsnDef` | `IsaSpec::parse()` | `IsaRegistry` 析构 | 与装载记录一致 |
| `BreakpointTable` | `DebugService` 构造 | `DebugService` 析构 | 与调试会话一致 |
| `RunContext` | `TestService::runSuite()` 每用例一次 | `RunContext::drop()` | **单用例，绝不跨用例复用** |
| `TestReport` / `CaseResult` | `TestReport::summarize()` | 持久化后由 DAO 管理 | 长期（可回溯历史报告） |
| `Divergence` | `CompareEngine` 或 `DiffService` | 持久化后由 DAO 管理 | 长期 |
| `Persistence` | 进程启动装配 | 进程退出 | 与进程一致 |
| 6 个领域服务 / `AuthFilter` / `QuotaGuard` / `StatusChannel` | 启动时依赖注入 | 进程退出 | 与进程一致，服务之间**不互相 `new`** |
| 视图类 | 前端框架（随路由） | 框架 | 随页面 |
| `HttpApiClient` / `StateStore` | 前端组合根（单例） | 应用退出 | 与应用一致 |

**两条硬约束**：

1. **禁止在业务代码里直接 `new EmulatorCore`。** 内核实例必须经 `CoreFactory` 创建——这是 NFR-Q2「用例之间互不影响」在代码层面的唯一保证点，也是后续若要换成进程隔离（SAD 阶段已列为演进项）时唯一需要改的位置。
2. **`RunContext` 是「一次性」对象**，`drop()` 后再使用属于编程错误（`状态图-RunContext.svg` 中 `Disposed` 不可回到 `Running`）。批量执行中图省事共享一个上下文，会直接导致 NFR-Q2 失效。

## 七、设计原则落实情况

| 原则 | 落实方式 | 可核查点 |
| --- | --- | --- |
| **信息隐藏** | 属性一律 private / protected，对外只暴露方法；`ArchState::snapshot()` 返回值对象而非内部数组引用 | 类图属性行的 `-` 标记 |
| **可见范围最小化** | 30 个方法为 private，集中在管道各级、校验子检查、解析内部函数 | 类图方法行的 `-` 标记 |
| **强内聚** | 一个类只有一个变更原因：`QuotaGuard` 只管限额、`AuthFilter` 只管鉴权（这是 SAD 把 `ApiController` 拆成三个构件的延续） | SS-6 类图 |
| **松耦合** | 服务之间不引用具体类，一律经 `IStore` / `IComparator` / `ICoreService` / `IToolchainPort` / `IRefSimPort` | 关系表第 25、31 行 |
| **单一职责** | `CompareEngine` 被两处复用而非各写一份；`ProcessRunner` 抽出两处适配的共性 | 关系表第 31 行、SS-4 类图 |
| **不开无谓的继承** | 全系统唯一继承链是 6 个服务 → `ServiceBase`；其余全是接口实现 | 类图图例 |
| **可测试性** | 内核零 Web 依赖（构建脚本强制）；`CompareEngine`、`IsaValidator` 均可在无服务框架下单元测试 | NFR-I2 |

## 八、与上游模型的一致性说明

### 8.1 本阶段新增的类（2 个）

| 新增类 | 理由 | 归属转换方式 |
| --- | --- | --- |
| `ServiceBase` | 7 个领域服务都需要日志、配置与事务模板；若各写一份，是 7 处重复。同时它是本设计里 **protected 的唯一承载者**——没有它，「确定可见范围」这条要求在本项目中会没有落点 | 方式三（多元素协作）的补充 |
| `CoreFactory` | NFR-Q2 要求内核实例按用例创建，必须有**集中的创建点**；否则 `new EmulatorCore` 会散落在 `TestService` / `DiffService` / `LoadService` 三处，后续改成进程隔离时无法一处改动 | 方式三 |

其余 6 个设计类（`StepResult` / `InsnDef` / `StateRecord` / `RunContext` / `BreakpointTable` / `TestReport`）在 SAD 中被记为「服务内部数据结构」，本阶段显式化——若不显式化，UC-07 的回退与 UC-08 的判定在实现时无从落笔。

### 8.2 与 SAD 接口清单的对应

SAD 5.10 列出 6 个 C++ 接口，本阶段给出具体签名（见第四章）。接口数量与名称**未增未减**。

### 8.4 分析类 → 设计类的转换方式统计

| 方式 | 项数 | 典型 |
| --- | --- | --- |
| 方式一（一职责一方法） | 6 | `IsaValidator::validate()`、`HttpGateway::handle()` |
| 方式二（一职责多方法） | 4 | `SessionService` 的 `login` / `createSession` / `createWorkspace` |
| 方式三（多元素协作） | 8 + 2（本阶段新增两项） | `EmulatorCore::step()` 的管道四级；`ServiceBase` 消除 7 服务样板；`CoreFactory` 集中内核创建 |

**方式三占比接近一半**，与 SAD 把系统拆成 7 个子系统直接相关——跨子系统协作只能由多个元素共同承担，这不是设计阶段的额外复杂化。
