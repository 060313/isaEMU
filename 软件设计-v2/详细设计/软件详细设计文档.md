## 1 文档概述

### 1.1 编写目的

本文档把《软件体系结构设计文档》中的 **8 个子系统 / 35 个构件**（"黑盒子"）细化为可直接指导编码的"白盒子"，回答五个问题：

1. 每个用例**如何**由设计类协作实现 —— 第 4 章；
2. 子系统的构件**如何**进一步组织 —— 第 5 章；
3. 每个设计类有哪些属性、方法与类间关系 —— 第 6 章；
4. 数据**存在哪里**、以何种形式组织、如何读写 —— 第 7 章；
5. 设计中**复用了哪些成熟模式**、为什么 —— 第 8 章。

按需求规格说明书 1.2 的约定，本文档**不覆盖**：界面视觉与交互细节（`uid` 阶段产出）、部署与构建形态（`sad` 阶段产出）、测试方案与测试用例集。

| 术语 / 缩略语 | 含义 | 说明 |
| --- | --- | --- |
| 设计类 | 构件内承担具体职责的类 | 共 **35 个**，与 SAD 构件一一对应，本阶段不新增不删除 |
| 契约接口 | 跨子系统调用的门面 | 共 **12 个**（含 SS-1 定义的 `IDecodeTable`） |

| 差分记录 | 记录"本步**改了哪些字段**"而非全量状态的数据形态 | `WriteOp`（最小单元）与 `StepRecord`（记录的载体） |
| 参数快照 | 只在**一次调用内**有意义的成员变量 | `EmulatorCore.limit_` / `tk_`，退出后不再有意义 |
| 谓词列 | 每条数据访问语句上追加的用户隔离条件列 | `owner_id` / `uid`，**11 张表全覆盖** |
| 组合根 | 全系统唯一的对象装配点 | `Bootstrapper`（SA-08） |
| 协作式取消 | 由被调用者主动检查取消标志、自行收敛的取消方式 | `CancelToken` + 批次边界检查 |
| 交叉表 | 为 n:m 关系新增的中间表 | 本设计 **n:m 为零**，故无交叉表 |
| 逻辑引用 | 存了标识但**不设外键**的引用 | `divergences.job_id`（任务不落库） |

## 2 系统概述

> 本章与《软件需求规格说明书》第 2 章、《软件体系结构设计文档》第 2 章保持一致，仅按详细设计表达的需要精简重述；**凡三者表述不一致处，以需求规格说明书为准**。

### 2.1 系统建设目标

本系统是一个**纯软件的 ISA 模拟系统**，以解释执行的方式重建指令级行为，并提供可视化、可调试、可批量验证、可与外部参考模拟器比对的能力。四项业务目标（来源：需求 2.5）：

| 编号 | 业务目标 | 对应问题 |
| --- | --- | --- |
| G1 | 让 ISA 学习者在无硬件条件下，以可视化单步的方式理解指令语义 | P1 指令执行过程不可观察 |
| G2 | 让工业芯片工程师在秒级完成指令级功能冒烟验证，不依赖 EDA 工具链 | P2 指令级功能验证成本高 |
| G3 | 让 ISA 工程师通过两套独立实现的行为对拍，发现规范本身的歧义与不一致 | P3 指令集规范本身的歧义难以发现 |
| G4 | 让机器语言程序员在可回退、可重放的模拟环境中调试裸机程序 | P4 机器语言与汇编程序缺乏轻量调试环境 |

### 2.2 主要功能

系统的功能归为**九个功能组**，共 **38 条功能需求**（`FR-1.1` ~ `FR-9.5`），覆盖 **14 个用例**。

| --- | --- | --- | --- | --- |

| ISA 描述装载 | 抽象边界、描述校验、装载与切换 | FR-1.1 ~ FR-1.3 | 3 | SS-2 |
| 程序装载 | 机器码 / 汇编源载入、运行初态配置、示例程序 | FR-2.1 ~ FR-2.4 | 4 | `LoadService` + SS-4 |
| 调试控制 | 单步、运行、暂停、复位、断点、运行到地址、历史回退 | FR-4.1 ~ FR-4.4 | 4 | `DebugService` + SS-1 |

### 2.3 边界和范围

**本期功能范围（本系统负责）**：ISA 描述装载与校验（首期 RISC-V RV32I）、程序装载与运行配置、指令解释执行、程序终止与运行期异常处理、指令级单步与断点调试、寄存器与内存可视化、示例程序与新手引导、测试用例组织与批量验证、与 Spike 的一致性对拍、集成 API、多用户会话与隔离。

**本期不在范围内**

| 排除项 | 说明 |
| --- | --- |
| 周期精确的微架构建模 | 不建模流水线、缓存时序，仅做体系结构级（功能级）模拟 |
| 完整外设与中断建模 | 仅处理约定的终止序列与运行期异常 |
| 操作系统级全系统仿真 | 不运行操作系统，面向裸机程序 |
| 第二套指令集的完整实现 | 本期仅在架构上保留 ISA 抽象边界 |
| QEMU 等其他外部参考模拟器的接入 | 本期对拍基准锁定 Spike |

**边界划分**

| 由本软件实现 | 由环境或第三方提供 |

## 3 设计目标和原则

### 3.1 详细设计欲达成的目标

体系结构层已定 T1 ~ T8（SAD 3.1），本节给出**详细设计层**的判据与落点（目标本身继承，判据细化）。

| 编号 | 目标 | 详细设计层的达成判据 | 落点 |
| --- | --- | --- | --- |
| T1 | 完整覆盖需求 | 38 条 FR 与 13 条 NFR 在**设计类的方法**上均有落点 | 4.7、6.4、附录 B |
| T2 | 关键路径低延迟 | 单步路径的调用链固定为 4 跳且无虚函数分发以外的开销 | 6.4.1 `cycle()` |
| T3 | 抽象边界成立 | 内核源码中不出现任何 RV32I 具体指令名；译码只经 `IDecodeTable` | 6.5.2 `Instruction.opClass` |
| T4 | 复用优先 | 本阶段**零新增第三方依赖** | 6.5 全部类型为自研值类型 |
| T5 | 双形态同源 | 差异收敛到 3 处配置点，业务代码零分支 | 2.5、7.2 |
| T6 | 支持 5 人并行 | 12 个契约接口在阶段一定稿且此后不再变 | 6.4.2 |
| T7 | 内核可独立验证 | 35 个构件**零继承**、依赖全为构造注入，可整体替换为测试替身 | 6.2.4 |
| T8 | 许可与交付合规 | 内核层零第三方链接（**NFR-C4**：新引入的第三方一律经 SS-4 适配层）；「热路径零业务概念」是另一条约束，见 **类设计 G-5** | 6.3.4 · NFR-C4 |

### 3.2 需实现的功能需求及其对详细设计的要求

| 需求组 | 对详细设计提出的要求 | 落点 |
| --- | --- | --- |
| FR-1.x ISA 描述装载 | 校验要能给出**逐行问题清单**而不是布尔；译码必须是 O(1) 查表 | `Issue` 值类型；`DecodeTable.rows_` 直表 |
| FR-2.x 程序装载 | 装载必须**整体替换**，不允许部分写入；「仅汇编不装载」要可单独调用 | `EmulatorCore.load`；`LoadService.assemble` / `loadProgram` |
| FR-3.x 执行内核 | 执行、状态、轨迹、终止四条变更原因必须落在四个类上；异常不得使进程崩溃 | SS-1 的 4 个类；`Result<T>` 不抛异常（类设计 G-6） |
| FR-4.x 调试控制 | 「运行至边界」的边界必须**有唯一定义**；回退不得依赖全量快照 | `RunMode` 五取值（D-1）；`Trace.rewindTo` 逆序撤销 |
| FR-5.x 状态可视化 | 前后端之间必须是**增量**，且增量要能定位到具体字段 | `StepDelta` + `WriteOp.index` |
| FR-6.x 测试验证 | 每个用例一个干净初态；两种判定模式复用同一引擎 | `TestService` 逐用例 `load + run`；`DiffScope.mode` |
| FR-7.x 一致性对拍 | 双方都要能输出"本步引发的写操作"，才能定位到差异字段 | `WriteOp` 是内核与参考侧的**共同数据形态** |

### 3.5 详细设计的十条总则

以下十条是本阶段的**编码级约定**，第 4 ~ 7 章的每一行都遵循它们，后续不再逐处重复。

**（一）类设计的六条总则**（第 6 章）

| # | 总则 | 内容 |
| --- | --- | --- |
| G-1 | **语言与命名** | 后端 C++17（SS-1 ~ SS-6、SS-8），前端 TypeScript 5（SS-7）。类名 `PascalCase`；方法 `camelCase`；后端成员变量**尾下划线**（`arch_`）、前端私有成员 `#` 前缀；常量 `k` 前缀（`kDefaultMask`）；文件名与类名一致 |
| G-2 | **值语义优先** | 跨构件传递的数据一律用不可变值类型，不用裸指针或可变引用；只有需要身份与生命周期的对象才是引用语义类 |
| G-3 | **构造与控制反转** | 跨子系统可见的类**构造私有**，实例只由 `Bootstrapper` 创建并注入；**全项目只有 `Bootstrapper::build` 里出现 `new`** |
| G-4 | **函数式核心** | 任何纯计算（译码、比对、终止判定、边界判定）不持有状态、不读全局、不写日志 |
| G-5 | **热路径零业务概念** | 内核与译码的代码里不出现配额、断点、用户、日志、事务等业务词 |
| G-6 | **错误用返回值不用异常** | 可预期的失败一律用 `Result<T>` 表达；异常只用于「不该发生的事」 |

**（二）数据设计的四条总则**（第 7 章）

| # | 总则 | 内容 |
| --- | --- | --- |
| G-1 | **谓词列命名统一** | 隔离谓词列一律叫 `owner_id`（用户表自身为 `uid`）。这让 `DbStore::scoped` 能**无条件**追加 `AND owner_id = :u`，不必为每张表记不同列名 |

| G-3 | **JSON 列的判据** | **只有整块读写的子结构**用 JSON 文档列；凡进入 `WHERE` / `ORDER BY` / 唯一约束的字段，一律用关系列 |
| G-4 | **存绝对时刻** | 过期时间等存绝对时刻（如 `expires_at = last_seen + sessionTimeout`），把过期判定留在 SQL 里，不必把 TTL 传进每次查询 |

#### 4.4.1 UC-01 注册与登录（P1）

![用例设计顺序图 UC-01](./图/用例设计顺序图-UC-01-注册与登录.svg)

**承载需求** FR-9.1、NFR-I2。**参与设计类** `SessionView` `AppShell` `HttpGateway` `SessionService` `IStore` `IIdGen`。

**实现方案**

1. 用户在 `SessionView` 提交用户名与口令；
2. `SessionView` 界面内校验（非空、口令长度、二次一致），不通过则禁用提交；
3. `SessionView` → `AppShell`：`login(cred)`；
4. `AppShell` → `HttpGateway`：`POST /api/sessions {cred}`；
5. `HttpGateway` → `SessionService`：`login(cred)`（路由由 `Router` 在网关内部完成）；
6. `SessionService` → `IStore`：`findCredential(username)`；
7. `IStore` → `SessionService`：凭据行（或空）；
8. `SessionService` 自调用：**先执行哑元 KDF**（不存在时也消耗同量时间），再校验口令哈希；失败时记 `ILogger` 并返回**具体失败原因**；
9. `SessionService` → `IIdGen`：`newToken()`；
10. `SessionService` → `IStore`：`saveSession(session)` / `initWorkspace(uid)`；
11. `SessionService` → `HttpGateway`：会话令牌 + 工作区句柄 + 当前 ISA；
12. `HttpGateway` → `AppShell`：`200 {token, workspace, isa}`；
13. `AppShell` 自调用：写入全局状态（token / workspace / isa），切换路由到 `/debug`；
14. `AppShell` → `SessionView`：登录成功；
15. `SessionView` 自调用：呈现结果提示条（成功 3 秒消失、失败常驻）；
16. `SessionView` → `AppShell`：**跳转 J-01（替换方向）**，进入主界面并触发 UC-06 取状态。

**关键决策**

- **口令校验是方式二**（⑧）：`findCredential` 与哈希比算是同一职责下的两步，任一失败都归入同一失败语义，向界面只暴露「账号不存在 / 口令错误 / 账号已停用」三类原因。
- **取数入口是 `findCredential`**：`User` 值类型不含任何验证材料，而哈希比算需要 `salt` / `iterations` / `kdf` —— 这三个值只在 `credentials` 表里（见 7.3.3）。它是 7.3.14 的「免谓词入口」之一。
- **工作区在登录时一并建立**（⑩）：对应分析类 `SessionController.createWorkspace`；隔离谓词由 `IStore` 在每条语句上附加（数据设计 G-1 / D-5），`SessionService` 不拼 SQL。
- **本地形态短路**：鉴权关闭时 ③ ~ ⑬ 由 `AppShell` 直接构造本地会话，随后执行 ⑯。这是 FR-9.2 双形态对等在会话链路上的落点。
- **J-01 是「替换」而非「前进」**：进入主界面后不保留 UI-01 的返回历史。

#### 4.4.2 UC-02 装载与管理 ISA 指令集（P1）

![用例设计顺序图 UC-02](./图/用例设计顺序图-UC-02-装载与管理ISA.svg)

**承载需求** FR-1.1 ~ FR-1.3。**参与设计类** `IsaView` `AppShell` `HttpGateway` `IsaService` `IsaLoader` `DecodeTable` `IStore`。

**实现方案**

1. ISA 工程师上传 ISA 描述文件；
2. `IsaView` → `AppShell`：`loadSpec(file)`；
3. `AppShell` → `HttpGateway`：`POST /api/isa {file}`；
4. `HttpGateway` → `IsaService`：`loadSpec(file)`；
5. `IsaService` → `IsaLoader`：`parse(file)`；
6. `IsaLoader` → `IsaService`：候选 ISA 描述；
7. `IsaLoader` 由 `IsaService` 自调用触发**三段校验**（指令集完备性 / 寄存器定义 / 编码域自洽），逐行产出 `Issue`；
8. `IsaService` → `IsaLoader`：`buildDecodeTable(spec)` 构建 O(1) 译码表；
9. `IsaLoader` → `IsaService`：译码表句柄（`const IDecodeTable&`）；
10. `IsaService` → `IStore`：`saveActive(spec)`；
11. `IsaService` → `HttpGateway`：装载结果 + 问题清单；
12. `HttpGateway` → `AppShell`：`200` 或 `422 {issues[]}`；
13. `AppShell` 自调用：更新全局状态 `currentIsa`；
14. `AppShell` → `IsaView`：装载结果；
15. `IsaView` 自调用：呈现结果提示条或问题清单（含 C-10 的重新校验入口）。

**关键决策**

- **`IsaSpec` 一拆为二**：`IsaLoader` 承担解析与校验（启动期、一次性），`DecodeTable` 承担译码表构建与查询（热路径、O(1)）。两者在性能特征与变更原因上都不同。
- **失败不切换**：校验不通过时返回 422 与问题清单，**保持上一套可用 ISA 生效**。这是 FR-1.3「不静默失败」在不破坏可用性上的推论。
- **⑧ 触发 SA-01**：`DecodeTable` 实现的是内核侧（SS-1）定义的 `IDecodeTable` 契约，SS-2 依赖 SS-1，而不是反过来。R1 收缩后 SS-5 只依赖 `IIsaProvider`，代码里不出现 `DecodeTable` 这个名字。

#### 4.4.3 UC-03 装载并配置待模拟程序（P0）

![用例设计顺序图 UC-03](./图/用例设计顺序图-UC-03-装载并配置程序.svg)

**承载需求** FR-2.1 ~ FR-2.4。**参与设计类** `LoadView` `AppShell` `LoadService` `ToolchainAdapter` `IProcessRunner` `EmulatorCore`。

**实现方案**

1. 用户提交汇编源或机器码 / ELF 映像，填写基址、起始 PC、栈指针、内存初值；
2. `LoadView` 界面内校验：十六进制格式、基址 4 字节对齐、起始 PC 落在映像范围内、栈指针对齐；不通过则提交按钮禁用；
3. `LoadView` → `AppShell` → `LoadService`：`loadProgram(src, base, initialState)`；
4. `LoadService` → `ToolchainAdapter`：`assemble(src)`；
5. `ToolchainAdapter` → `IProcessRunner`：`run(toolchain, src)`（起子进程 + 管道）；
6. `IProcessRunner` → `ToolchainAdapter`：机器码映像 / 错误行；
7. `ToolchainAdapter` → `LoadService`：映像 / 错误行；
8. `LoadService` 自调用：**失败分支** —— 错误行回填 UI-03；工具链缺失给告警条（FR-2.2）；
9. `LoadService` → `EmulatorCore`：`load(image, base, initialState)`；
10. `EmulatorCore` → `LoadService`：就绪（PC / SP / 内存初值已写入 `ArchState`）；
11. `LoadService` → `LoadView`：装载结果 + 反汇编预览；
12. `LoadView` 自调用：呈现摘要与就绪提示条（C-09 的进度条）；
13. **跳转 J-13（返回方向）**：回到主界面并刷新四类视图。

**关键决策**

- **适配器与进程管理分离**：`ToolchainAdapter` 只负责"工具链语义"（命令拼装、输出解析），`IProcessRunner` 负责"进程语义"（起进程、喂输入、读输出、超时回收）。两者被两个适配器共用同一份实现（SA-06）。
- **「仅汇编不装载」可单独调用**：④ ~ ⑦ 与 ⑨ 是两段可分离的调用，支持 UI-03 上"只汇编看反汇编预览"的用法。
- **⑨ 之前不做部分写入**：`EmulatorCore.load` 是整体替换，不是逐段写入；否则失败时会留下半装载状态。

#### 4.4.4 UC-04 单步与连续执行（P0）

![用例设计顺序图 UC-04](./图/用例设计顺序图-UC-04-单步与连续执行.svg)

**承载需求** FR-3.1 ~ FR-3.5、NFR-Q1（10⁷ 条/秒）、NFR-Q2（10⁸ 条连续执行）、NFR-Q3。**参与设计类** `DebugView` `AppShell` `DebugService` `EmulatorCore` `ArchState` `Trace` `TerminationGuard`。

**实现方案**

1. 用户点「单步」/「连续运行」/「运行 N 步」；
2. `DebugView` → `AppShell` → `DebugService`：`execute(mode, param, n, limit)`；
3. `DebugService` → `EmulatorCore`：`step(1)` / `run(mode, param, limit, tk)`；
4. `EmulatorCore` 自调用：取指—译码—执行—写回主循环（`cycle()`，查 `IDecodeTable`）；
5. `EmulatorCore` → `ArchState`：`apply(writes)` 更新 PC / GPR / 内存 / CSR；
6. `EmulatorCore` → `Trace`：`append(stepRecord)` 记录本步写操作（差分）；
7. `EmulatorCore` → `TerminationGuard`：`check(state)` / `captureFault()`；
8. `TerminationGuard` → `EmulatorCore`：未终止 / 终止标志 + 异常现场；
9. `EmulatorCore` → `DebugService`：状态增量（`StepDelta`）+ `RunReason`；
10. `DebugService` → `DebugView`：状态与轨迹推送；
11. `DebugView` 自调用：高亮本步变化（NFR-Q3 的界面落点）；
12. `DebugView` 自调用：刷新四类视图（B/C 常驻，D/E 选项卡）。

**关键决策**

- **差分写操作而非全量快照**（⑤⑥）：`ArchState.apply` 收到的是"本步实际改了哪些字段"，`Trace` 记的也是同一份。这是 SA-13 的落点：**一份记录同时服务 FR-3.3 / FR-4.4 / FR-7.2**。
- **执行循环不持有配额**（③）：指令条数上限以**参数**随运行请求下发（`limit`）；内核只按步计数、到达上限即返回，由界面按 C-02 呈现"已执行条数 / 上限"。内核代码中不出现"配额"这一业务概念（数据设计 / 类设计 G-5，SA-05）。
- **终止判定独立**（⑦）：FR-3.4 与 FR-3.5 不写在执行循环里，避免执行循环同时承担"跑"和"停"两种变更原因。
- **轨迹可关闭**：关闭轨迹时 ⑥ 与 ⑧ 一并关闭，同时回退能力关闭 —— 保证关闭轨迹时的吞吐量要求不受影响（NFR-Q1）。

#### 4.4.5 UC-05 设置与管理断点（P1）

![用例设计顺序图 UC-05](./图/用例设计顺序图-UC-05-断点管理.svg)

**承载需求** FR-4.2。**参与设计类** `DebugView` `AppShell` `DebugService` `BreakpointTable` `EmulatorCore`。

**实现方案**

1. 用户设 / 删 / 启用 / 禁用 / 清除断点；
2. `DebugView` → `DebugService`：`registerBreakpoint(addr, op)`；
3. `DebugService` → `BreakpointTable`：`add` / `remove` / `toggle(addr)`；
4. `BreakpointTable` → `DebugService`：断点列表；
5. `DebugView` 自调用：刷新断点列表（C-03 的全部启用 / 禁用 / 清除按钮组）；
6. 用户点「连续运行」；
7. `DebugView` → `DebugService`：`execute(RunN/Continue)`；
8. `DebugService` 自调用：**循环** —— 逐步执行 + 查断点表；
9. `DebugService` → `EmulatorCore`：`step(1)`；
10. `DebugService` → `BreakpointTable`：`checkHit(pc)`；
11. `BreakpointTable` → `DebugService`：命中 → 退出循环；
12. `DebugService` → `DebugView`：暂停并高亮命中行；
13. `DebugView` 自调用：断点命中呈现。

**关键决策**

- **断点表放 SS-5 而不是 SS-1**：内核不持有断点状态，由 `DebugService` 在每步之后查表。代价是"运行到断点"需要服务层参与每步判定，收益是内核零业务概念、可独立编译与单测。
- **循环在服务层展开**（⑧ ~ ⑪）：交互模型只给了"检查断点命中"一条消息；解域把它显式化为"执行一步 + 查表"的循环，属方式三。连续运行到断点的热路径因此有两次跨构件调用 / 步，**只在开启断点时才付出**。
- **断点可跨会话保留**：`BreakpointTable` 经 `IStore` 持久化（`saveBreakpoints` / `loadBreakpoints`，见 7.4）。

#### 4.4.6 UC-06 查看架构状态与执行轨迹（P1）

![用例设计顺序图 UC-06](./图/用例设计顺序图-UC-06-查看状态与轨迹.svg)

**承载需求** FR-5.1 ~ FR-5.4、NFR-Q3。**参与设计类** `DebugView` `AppShell` `DebugService` `ArchState` `Trace`（R2 收缩后一律经 `ICoreService` 访问）。

**实现方案**

1. 用户切换视图（寄存器 / 内存 / 反汇编 / 轨迹）；

4. `EmulatorCore` → `ArchState`：`snapshot(scope)`；
5. `ArchState` → `EmulatorCore` → `DebugService`：架构状态快照（`StateSnapshot`）；

#### 4.4.7 UC-07 回退执行历史（P1）

![用例设计顺序图 UC-07](./图/用例设计顺序图-UC-07-回退执行历史.svg)

**承载需求** FR-4.4。**参与设计类** `DebugView` `AppShell` `DebugService` `Trace` `ArchState`（经 `ICoreService`）。

**实现方案**

1. 用户选择历史某一步；
2. `DebugView` → `DebugService`：`rollback(targetStep)`；
3. `DebugService` → `EmulatorCore`：`rollback(targetStep)`（R2 后由内核统一代理）；
4. `EmulatorCore` → `Trace`：`rewindTo(targetStep)`；
5. `Trace` 自调用：按**逆序撤销**目标步之后的写操作（差分回退）；
6. `Trace` → `EmulatorCore`：目标步的架构状态；
7. `EmulatorCore` → `ArchState`：`restore(snapshot)`；
8. `EmulatorCore` → `DebugService`：状态已回退；
9. `DebugService` → `DebugView`：四类视图同步刷新。

**关键决策**

- **差分 / 日志式回退**（SA-13 的落地）：按逆序撤销写操作，**不保存全量快照**。全量快照在一次 10⁶ 步调试会话中内存量不可接受。
- **R2 新增 `ICoreService.restore`（D-2）**：用例设计阶段写的是 `DebugService → ArchState.restore(s)`，本步改为 `ICoreService.restore(...)`，使「谁能改架构状态」在类型系统上唯一为 `EmulatorCore`。
- **被裁剪的区段不可回退**：轨迹超限时按 SA-13 丢弃最旧的不可回退段，此时界面按 **C-02（已执行条数 / 上限）与 C-04（执行类按钮的禁用规则）** 明确置灰并提示，不做静默失败。
- **回退后继续执行会截断该步之后的轨迹段**（本步新增）：线性差分日志的自然结果，界面在读档后明确提示"后续轨迹已作废"。

#### 4.4.10 UC-10 发起 ISA 一致性对拍（P1）

![用例设计顺序图 UC-10](./图/用例设计顺序图-UC-10-一致性对拍.svg)

**实现方案**

6. `RefSimAdapter` → `DiffService`：参考模拟器状态序列；

14. `WorkspaceView` 自调用：视图刷新。

**关键决策**

- **持久化下沉 SS-8**：`WorkspaceService` 只负责领域语义（哪些制品入包、版本与冲突规则），数据访问经 `IStore`。
- **恢复后不自动执行**：恢复到工作区初态即停，由用户按下"单步 / 运行"才执行。这样"加载"与"运行"是两件事，符合用户对调试器的预期。
- **双形态对等**（FR-9.2）：本地走 SQLite（`workspace.db`）、云端走 PostgreSQL，**⑪ ~ ⑭ 的调用完全一致**，差异只在 `Bootstrapper` 按 `IConfig.dbDriver` 选择驱动。
- **选择性保存**（①）：`selection` 参数承载"只存程序""只存用例集"等用法，对应 UI-09 的选择性保存入口。

#### 4.4.13 UC-13 通过集成 API 驱动模拟（P1）

![用例设计顺序图 UC-13](./图/用例设计顺序图-UC-13-集成API驱动模拟.svg)

**承载需求** FR-8.1 ~ FR-8.3、NFR-Q5。**参与设计类** `HttpGateway` `AccessGuard` `Router` `EmulatorCore` `TestService` `DiffService`。

**实现方案**

1. 集成 API 客户端调用 API（凭据、操作、参数）；
2. `HttpGateway` → `AccessGuard`：`authorize(cred)` / `checkQuota(uid, op)`；
3. `AccessGuard` → `HttpGateway`：通过 / 拒绝（401 / 429）；
4. `HttpGateway` → `Router`：`route(op, params)`；
5. `Router` 自调用：参数绑定与 Schema 校验；
6. `Router` → `EmulatorCore`（经会话上下文）：`load` / `step` / `run`（分支一：装载 · 单步 · 运行）；
7. `Router` → `TestService`：`runSuite(suiteId, mode)`（分支二：执行测试）；
8. `Router` → `DiffService`：`start(program, scope)`（分支三：发起对拍）；
9. `Router` → `HttpGateway`：结构化响应 `{result}` / `{error}`；
10. `HttpGateway` → 客户端：`200` / `4xx`；
11. `HttpGateway` 自调用：（WebSocket）主动推送批量进度（FR-6.4）。

**关键决策**

- **通道与 UC-08 完全共用**：`HttpGateway → AccessGuard → Router → 领域服务` 同一条链；分析类 `ApiEndpoint` 的边界职责与控制类 `ApiController` 的分发职责在此合并。
- **⑥⑦⑧ 三选一**：同一请求只走其中一条分支；`Router` 按 `op` 分发，分发表（`Router.table_`）是可独立替换的机制（增删接口不改鉴权代码）。
- **装载 / 单步走 `ICoreService`**：与 UC-04 一致，仅调用方由 `DebugService` 换成 `Router` —— 这使接口文档与调用示例（FR-8.3）与 REST / WS 契约**可以同步维护**。
- **限流在入口不在内核**：`AccessGuard.checkInstrLimit(n)` 在请求受理时判定，内核不感知（SA-05）。

#### 4.4.14 UC-14 管理用户与资源配额（P2）

![用例设计顺序图 UC-14](./图/用例设计顺序图-UC-14-用户与配额管理.svg)

**承载需求** FR-9.4、FR-9.5。**参与设计类** `SessionView` `AppShell` `HttpGateway` `SessionService` `IStore`。

**实现方案**

1. 平台管理员查看用户列表与资源占用；
2. `SessionView` → `AppShell` → `HttpGateway` → `SessionService`：`listUsers()` / `queryUsage(uid)`；
3. `HttpGateway` → `SessionService`：`GET /api/users`；
4. `SessionService` → `IStore`：`queryUsers()` / `queryUsage(uid)`（O-05 / O-06）；
5. `IStore` → `SessionService`：用户列表 + 占用情况；
6. `SessionService` → `HttpGateway` → `AppShell`：`200`；
7. `SessionView` 自调用：呈现用户与配额表（页面模板 B）；
8. 管理员调整配额或停用账号（**二次确认后**）；
9. `SessionView` → `SessionService`：`updateUser(uid, patch)`；
10. `SessionService` → `IStore`：`saveUser(u, user)`；
11. `SessionService` → `SessionView`：操作结果；
12. `SessionView` 自调用：确认提示（C-17 危险操作二次确认）。

**关键决策**

- **配额的作用点在 `AccessGuard`**：本用例只改配额**数据**、不改检查逻辑；UI-02 状态栏显示的"上限"唯一来源是运行配置（`IConfig`），与 UC-04 下发到内核的 `limit` 同源 —— 这是《用户界面设计评审意见》⑦-1（C-02 来源悬空）在详细设计上的收口。
- **危险操作二次确认**（⑧）：停用账号按 C-17 统一二次确认，确认后才发出 ⑨。
- **方式二**：`listUsers` / `updateUser` 是同一职责（用户与配额管理）下的两个独立方法。
- **`queryUsage` 是三段组装**（DD-4）：窗口计数取自 `usage_counters`，活跃会话数与工作区占用**派生**自 `sessions` / `workspaces`，不落冗余计数器。

本章按技能的四个动作组织：可见范围（6.1）→ 类间关系（6.2）→ 属性（6.3）→ 方法（6.4）；共享类型单列（6.5）；三个条件项（精化类图、状态图、活动图）见 6.6 ~ 6.8。本章新作出的 8 条设计判断集中在 6.9 与附录 C。

### 6.1 可见范围的确定

**三档类级可见范围**。技能要求「尽可能缩小可见范围」。C++ 里类的可见范围不由 `public/private` 表达（那是成员的），而由**导出哪些头文件**表达；本设计把它规约为三档，并在 TS 侧用模块 `export` 对应：

| 档 | 名称 | C++ 对应 | TS 对应 | 含义 |
| --- | --- | --- | --- | --- |
| 1 | **公开契约** | 导出到 `include/` 的声名 | `export` 到 `src/api/` | 可被**其他子系统**引用 |
| 2 | **装配可见** | 仅在子系统内部头文件中声明 | 模块内导出，不进 `src/api/` | 仅 **`Bootstrapper`** 与**同子系统**可见 |
| 3 | **构件内部** | `.cpp` 内匿名命名空间 / 不导出 | 文件内非导出声明 | 仅**同一构件内**可见 |

**判定规则**（三条，按序应用）：**P1** 实例是否需要跨子系统传递？→ 是则档 1（但**优先改为传递其接口**）；**P2** 是否只需被装配者创建、由其他构件经接口使用？→ 是则档 2；**P3** 是否只在一个构件的内部实现中出现？→ 是则档 3。

**35 个设计类的可见范围**

| 子系统 | 类 | 档 | 依据 |
| --- | --- | --- | --- |
| SS-1 | `EmulatorCore` / `ArchState` / `Trace` / `TerminationGuard` | **2 装配** | 只被 `SessionContext` / `EmulatorCore` 创建与持有，外部一律经 `ICoreService`（P2 + R2） |
| SS-2 | `IsaLoader` / `DecodeTable` | **2 装配** | 只被 `Bootstrapper` / `IsaLoader` 创建；对内核经 `IDecodeTable`、对 SS-5 经 `IIsaProvider` |
| SS-3 | `CompareEngine` | **2 装配** | 被 SS-5 经 `ICompareService` 使用（无状态单例） |
| SS-3 | `DiffScope` / `Divergence` | **1 公开** | 值类型 / 数据对象：跨子系统构造与传递（P1） |
| SS-4 | `ToolchainAdapter` / `RefSimAdapter` | **2 装配** | 被 SS-5 经 `IAssembler` / `IRefSim` 使用 |
| SS-5 | 7 个领域服务 | **2 装配** | 被 SS-6 经各自接口使用（`SessionService` 另有同子系统直引，见 R3） |
| SS-5（**附列**） | `SessionContext` / `BreakpointTable` | **3 构件内部** | 只被 `SessionService` / `DebugService` 管理与传递（`contextOf` 返回引用）。两者是**构件的内部类**，**不计入 35 个设计类**（见下方的统计口径） |
| SS-6 | `HttpGateway` / `Router` / `AccessGuard` | **2 装配** | 只被 `Bootstrapper` 创建，仅供网络层调用 |
| SS-6 | `Bootstrapper` | **1 公开** | 由 `main()` 调用（P1） |
| SS-7 | `AppShell` + 7 个 `«page»` | **1 公开** | 7 个页面都引用外壳；页面由路由按需加载 |
| SS-8 | `IStore` / `IConfig` / `ILogger` / `IIdGen` / `IProcessRunner` | **1 公开** | 跨层引用（P1） |
| SS-8 | `DbStore` / `FileConfig` / `StdLogger` / `UuidGen` / `ProcRunner` | **2 装配** | 只被 `Bootstrapper` 创建（**不计入 35 个设计类**，属构件内部实现） |

**统计口径**：本表**只列 35 个设计类**（= SAD 的 35 个构件，一一对应）。其中**档 1（公开契约）16 个**、**档 2（装配可见）19 个**、**档 3（构件内部）0 个** —— 16 + 19 = 35。

- **档 1 的 16 个** = `DiffScope` / `Divergence`（2）+ `Bootstrapper`（1）+ SS-7 的 8 个（`AppShell` + 7 个 `«page»`）+ SS-8 的 5 个接口。档 1 占比高，是因为**数据结构本身就要求跨子系统传递**；凡是「能力」都已被收敛为接口（档 1 里是接口而非实现类）。
- **档 3 在 35 个设计类里为空**：`SessionContext` / `BreakpointTable` 虽是档 3，但它们是 `SessionService` / `DebugService` 两个构件的**内部类**（上表已标「附列」），不计入 35。另有一类档 3 成员是**属性式的内部索引结构**（如 `DecodeTable.rows_` / `wide_`），它们不是类，不参与本表统计。

> **值类型不进入本表**：`TestSuite` / `TestCase` / `TestReport` / `CaseResult` / `Program` / `Workspace` / `Credential` / `User` / `Usage` / `Attribution` 等是**值对象 / 数据对象**（1.4 的术语定义已把「设计类」与「值类型」分开），由 SS-5 构造、被 SS-6 序列化为响应；它们的权威清单在 **6.5.2**，一律属档 1。把两者混进同一张表会让三档统计与「35 个设计类」对不上 —— 这正是评审 ①-3 / ⑥-3 的修正点。

**成员级可见性规则**

| 成员类别 | 可见性 | 说明 |
| --- | --- | --- |
| 数据成员 | 一律 `private` | 无例外 |
| 只读访问器 | `public`，且带 `const` | 值类型与数据对象的只读字段（如 `Divergence.stepNo`） |
| 契约方法 | `public` | 接口声明的方法 |
| 构件内部协作方法 | `private` | 如 `EmulatorCore::cycle()`、`IsaLoader::threeStage()` |
| 构造 / 析构 | 见类设计 G-3 | 跨子系统类私有构造；值类型公开构造 |
| 静态工厂 | `public static` | `DecodeTable::build()`、`DiffScope::preset()` |

**明确不做**：不使用继承（`protected` 因此零出现）、不用 `friend`。跨类的内部访问一律经接口或值类型。

**三处「缩小可见范围」的实例**（本步真正的查漏补缺，每处都对应一个上游表述不够精确的地方）：

| # | 收缩 | 改前 | 改后 | 收益 |
| --- | --- | --- | --- | --- |
| **R1** | 跨子系统传递的是**接口**而非实现类 | UC-02 写的是 `IsaService → DecodeTable.build(spec)`，即 SS-5 直接依赖 SS-2 的具体类 | 改为 SS-5 只依赖 **`IIsaProvider`**；`DecodeTable` 由 `IsaLoader` 创建并只在 SS-2 内可见 | SS-5 的代码里不出现 `DecodeTable` 这个名字；换一套译码表实现不影响 SS-5 |
| **R2** | `ArchState` / `Trace` 从「服务层可访问」收缩为「装配可见」 | UC-06 / UC-07 写的是 `DebugService → ArchState.snapshot()` / `ArchState.restore(s)` | 两者降为**档 2**，SS-5 一律经 `ICoreService.reads/restore` 访问；`ICoreService` 因此**新增 `restore(StateSnapshot)`** | 「谁能改架构状态」在类型系统上唯一：只有 `EmulatorCore`。防止「服务层绕过内核直接改状态」这类会破坏 SA-13 的写法 |
| **R3** | 会话上下文不暴露内核的**所有权** | UC-04 写的是 `DebugService → EmulatorCore.step(1)`，隐含「服务持有内核引用」 | `DebugService` 等 5 个服务经 `SessionService.contextOf(token)` 取 `SessionContext&`，再 `.core()` 取 `ICoreService&`；`SessionContext` 为**档 3**，`core_` 的 `unique_ptr` 所有权不对外暴露 | 内核实例的生命周期只有 `SessionContext` 一个负责人（SA-03 的落点）；服务层拿到的是引用，销毁不了它 |

> **R2 与 R3 是对用例设计阶段的两处修正**，已登记为 D-2、D-3（附录 C、附录 D）。两处都**不改变用例实现方案的协作序列**，只改变了调用点的门面（各多一跳转发）。

#### 6.2.4 强内聚、松耦合的证据

**强内聚（三条）**：① **组合关系 = 内聚边界** —— 8 组 ◆ 的「部分」都只能由「整体」创建与释放，任何一个部分都**不被第二个整体引用**；② **n:m 为零** —— 不存在「两个聚合共享同一批可变子对象」这种最容易产生一致性问题的结构；③ **SS-3 无属性** —— `CompareEngine` 是纯粹算法构件，它的变更只可能来自比对规则本身。

**松耦合（三条）**：① 跨子系统的 9 组关联中 **7 组的目标是接口**，唯一两个非接口目标（`SessionService`）已在 R3 说明必要性，**没有任何一处跨子系统关联到具体实现类**；② **依赖方向单向无环**，与 SAD 5.8 一致，唯一反向的 I-02 由 SA-01 消解；③ **属性里没有全局变量、单例访问器、服务定位器**，所有依赖都是构造注入的成员指针，因此任何构件都能在单测里被替换成测试替身（NFR-I2 的支撑）。

### 6.3 属性的精化

#### 6.3.1 属性形式规则

| 形式 | 写法 | 何时用 | 判据 |
| --- | --- | --- | --- |
| **组合形式** | `unique_ptr<X> x_` | 整体-部分，部分随整体销毁 | 关系表里是 ◆ 或 ◇（服务持有） |
| **关联形式** | `X* x_`（非拥有）或 `X& x_` | 长期持有但不是自己的 | 关系表里是 ─ 或由构造注入的依赖 |
| **值形式** | `X x_` / `const X x_` | 不可变值类型、枚举、基本类型 | 无身份与生命周期 |
| **集合形式** | `map<..>` / `vector<..>` / `deque<..>` / `set<..>` | 一对多 | 重数是 1:n / 0:n |
| **只读形式** | `public const` 成员或只读访问器 | 值类型与数据对象的对外字段 | 构造后不再变更 |

**三条细则**：① **不用 `shared_ptr`** —— 所有权必须唯一（类设计 G-3）；`CompareEngine` 被两个服务共享，但它是**无状态单例**，各持裸指针即可；② **裸指针表示「非拥有」**，且一律在构造时注入、生命周期长于持有者（由 `Bootstrapper` 的装配顺序保证）；③ **`optional<T>` 表达「可空的值」**，不用空指针（`fault_` / `attr_` / `snapshot_` / `program_`）。

### 6.4 方法的精化

**方法签名规则**

| 规则 | 内容 |
| --- | --- |
| **参数命名** | 全小写驼峰；单字母缩写仅用于**高频且语义明确**者（`u: UserId` / `t: Token` / `a: Addr` / `n: size_t` / `dt: const IDecodeTable&`），其余一律具名（`init` / `scope` / `target`） |
| **参数传递** | 小值类型**按值**（`Addr` / `uint32_t` / 枚举）；大值类型按 `const&`（`Image` / `StateSnapshot` / `IsaSpec`）；需要写入的用 `span<const T>`（只读视图）或 `T&`（输出参数，本设计仅用一次，见 `apply`） |
| **返回** | 可预期失败一律 `Result<T>`（类设计 G-6）；可能无结果用 `optional<T>`；可能多个用 `span<const T>`（避免拷贝大序列）或 `vector<T>` |
| **作用范围** | 契约方法 `public`；构件内部协作 `private`；静态工厂 `public static`。**不使用 `protected`**（无继承） |
| **不抛异常** | 除 `std::bad_alloc` 一类不可恢复错误外，方法都不抛。注释以 `@pre` / `@post` / `@ret` 三段说明 |

**6 处方法的拆分与合并**

| # | 动作 | 内容 | 理由 |
| --- | --- | --- | --- |
| 1 | **拆分** | `EmulatorCore::execute()` → `cycle()` + `atBoundary()` + `deliver()` | 执行、边界判定、增量组装三种职责，变更原因不同 |
| 2 | **拆分** | `IsaLoader::load()` → `parse()` + `threeStage()` | 解析失败与校验失败是两类错误，分开才能各自给出行号 |
| 3 | **拆分** | `HttpGateway::handle()` → `unwrap()` + `wrap()` | 入站与出站在错误处理上不对称（前者要解析失败、后者要统一状态码） |
| 4 | **合并** | `ToolchainAdapter` **不再提供** `assembleOnly`，只保留 `assemble`（**D-7**） | 两者是同一段逻辑（都只到汇编为止），差别只在**调用方要不要接着调 `load`**。「仅汇编不装载」的**决策点在 `LoadService`**（调用方）：调用 `assemble` 后不调 `loadProgram` 即是。少一个方法，且语义更准确 |
| 5 | **新增**（对象创建） | `DecodeTable::build` / `DiffScope::preset` / `SessionContext` 构造 | 静态工厂让不可变对象有唯一构建入口 |
| 6 | **新增**（对象删除） | `SessionContext::expired` + `SessionService::reap` | 无显式 `dispose`，以「移出 `live_` 即析构」表达释放 |

**对象的创建与销毁：三条边界**

1. **只有 `Bootstrapper` 与 `SessionContext` 两处出现 `new`**，其余全部是值构造或 `unique_ptr` 的移交。这条约定可用静态检查（`grep -n "new " src/` 只应命中两处）在 CI 里强制。
2. **内核实例的销毁点唯一**：`SessionContext` 被移出 `live_` 的那一刻。不设「手动释放内核」的接口 —— 否则会出现「会话还在但没有内核」的非法态。
3. **不需要显式的 `dispose()` / `close()`**：本设计中没有需要「手动归还」的资源句柄（数据库连接由连接池的 RAII 管理，子进程由 `ProcRunner` 即起即收）。故不引入技能提到的「对象删除方法」，以析构代替。

**`CancelToken` 单列说明（本步引入的原语）**

| 项 | 内容 |
| --- | --- |
| 形式 | 值语义的小对象，内部持 `shared_ptr<atomic<bool>>`（**全设计唯一使用共享所有权的地方**，因为多个执行者需要看到同一个标志） |
| 方法 | `cancel() : void`（置位）、`isCancelled() : bool`（读）、`reset() : void` |
| 检查点 | 内核：每 **`IConfig.cancelCheckInterval`** 步（默认 **4096**，`steps_ % interval == 0`）读一次；子进程：`waitFor` 的轮询周期内读一次 |
| 为什么不用 `std::stop_token` | C++20 的 `stop_token` 是更好的选择，但本项目工具链定为 C++17（SAD 5.1.4 的构建约束）。若升级到 C++20，本类型的实现可直接换成 `std::stop_source`，**签名不变** |
| 为什么用 `shared_ptr` 而非引用 | 取消标志的生命周期必须**长于所有执行者**：`JobEntry` 可能先被清理而内核仍在收尾。用共享所有权让标志随最后一个持有者释放 |

**值类型的四条约定**

1. **不可变**：所有字段 `const` 或用值语义整体替换；需要「修改」时构造新值（如 `DiffScope.configure` 内部整体重建）。
2. **可比较**：需要参与比对的类型（`WriteOp` / `FieldDiff` / `StateSnapshot`）提供 `operator==`，`CompareEngine` 直接用它，不写字段逐项比较。
3. **可序列化**：跨进程（REST / WS）与持久化的类型提供 `toJson` / `fromJson`（nlohmann/json），且**版本化**（`WorkspaceRow` 带 `version`，为格式演进留余地）。
4. **不带行为**：值类型不写业务方法（`Divergence::update` 是唯一例外，因为它的归因状态需要就地修改且需要版本号语义）。

## 7 数据设计

### 7.1 需要持久保存的数据

#### 7.1.1 判定口径

技能要求「根据需求模型和**类设计模型**」确定持久化范围。本设计采用**双向核对**：

1. **自下而上**：类设计阶段已把「持久化能力」收敛成 5 个基础接口之一 —— `IStore`。因此**凡出现在 `IStore` 方法签名里的类或值类型，都是持久化候选**；不在其中的默认不持久化。
2. **自上而下**：需求中凡出现「持久化 / 保存 / 加载 / 记录 / 报告 / 账号 / 配额」的条目，必须有对应的表或列落点。

两条路径的交集即持久化范围；只有一侧命中的，逐一解释（见 7.1.3）。

#### 7.1.2 持久化清单

`IStore` 的 **18 个方法**（类设计 15 个 + 本步新增 3 个：`findCredential` / `queryWorkspaces` / `queryReports`，见 DD-1 / DD-5）共涉及 **9 组持久数据**，落成 **11 张表**：

| 组 | 持久实体 | 类设计来源 | `IStore` 方法 | 表 |
| --- | --- | --- | --- | --- |
| 1 | 用户身份 | `User(uid, name, role, quota, status)` | `findUser` / `findUserByName` / `saveUser` / `queryUsers` | `users`（T-01） |
| 2 | 用户凭据 | **新增** `CredentialRow`（DD-1） | **新增** `findCredential`（DD-1） | `credentials`（T-02） |
| 3 | 资源用量 | `Usage(sessions, requests, instr, bytes)` | `queryUsage` | `usage_counters`（T-03）+ 2 处派生（DD-4） |
| 4 | 运行会话 | `SessionRow(token, uid, wsId, isaId, createdAt, lastSeen, expiresAt, endedAt)` | `saveSession` / `dropSession` | `sessions`（T-04） |
| 5 | 工作区 | `Workspace` / `WorkspaceRow` / `WorkspaceBrief` | `putWorkspace` / `getWorkspace` / **新增** `queryWorkspaces`（DD-5） | `workspaces`（T-05） |
| 6 | 用例集与用例 | `TestSuite` / `TestCase` | 随 `putWorkspace` / `getWorkspace`（**同一事务 T-1**） | `test_suites`（T-06）/ `test_cases`（T-07） |
| 7 | 测试报告与用例结果 | `TestReport` / `CaseResult` | `saveReport` / `getReport` / **新增** `queryReports`（DD-5） | `test_reports`（T-08）/ `report_cases`（T-09） |
| 8 | 断点表 | `BreakpointRow` / `Breakpoint` | `saveBreakpoints` / `loadBreakpoints` | `breakpoints`（T-10） |
| 9 | 分歧记录与归因 | `Divergence` / `DivergenceRow` | `saveDivergence` / `queryDivergence` | `divergences`（T-11） |

> 第 6 组不出现在 `IStore` 方法签名里（它没有独立方法），但它是 `Workspace` 的组合子结构，随第 5 组一起持久化 —— 这是 7.1.4 判据② 的作用。

#### 7.1.3 明确不持久化的数据（11 项）

**「明确不持久化」与「忘了做」在评审时长得一样**，故逐项列出并给理由：

| # | 数据 | 类设计来源 | 为什么不持久化 |
| --- | --- | --- | --- |
| 1 | `ArchState`（`pc_` / `gpr_` / `csr_` / `mem_`） | SS-1 | **会话运行时状态**。SA-03 明确「会话销毁时释放内核实例与内存映像」；把 `mem_` 落库会让「4 GiB 稀疏映像」变成「每会话一份可持久化的地址空间」，成本与语义都不成立 |
| 2 | `Trace.rec_`（`StepRecord` / `WriteOp`） | SS-1 | **容量与热路径双约束**。NFR-Q1 要求 10⁷ 条/秒吞吐，每条都落库不可行；`cap_` 上限 1 048 576 条也说明它是**有界内存缓冲**（SA-13 的「轨迹可裁剪」）。**回退能力因此只在会话内有效** —— 这是 SA-13 的既定语义，不是缺陷 |
| 3 | `TerminationGuard`（`last_` / `halted_` / `fault_`） | SS-1 | 判定过程的中间状态；`FaultRecord` 作为异常现场**随报告 / 分歧记录**带走，本体不落库 |
| 4 | `DecodeTable`（`rows_` / `wide_`） | SS-2 | **可由 `IsaSpec` 重建**（`DecodeTable::build`）。落库等于存一份可推导的直表，且直表长度 `1 << kMaxEncBits` 体积不小 |
| 5 | `IsaSpec` 本体 | SS-2 | ISA 描述由源文件 / 内联文本经 `IsaService.loadSpec` 装载（FR-1.2），`IsaLoader.tables_` 是应用级单例。会话只持久化 `SpecId`（`sessions.isa_id`），不存描述正文 —— 这样「换一份描述」不需要数据迁移 |
| 6 | `JobEntry` / `CancelToken` | SS-6 | **任务是一次性的**：`JobState` 到 `Finalized` 即终结（状态图③）。任务的**产物**（报告、分歧）才落库 |
| 7 | `ToolchainSpec` / `RunSpec` / `RunOutcome` / `Disasm` | SS-4 | 过程数据，每次调用重新产生 |
| 8 | `HttpGateway.ws_`（连接注册表） | SS-6 | 进程内资源，随进程销毁；重连即可重建 |
| 9 | `AccessGuard.rate_`（滑动窗） | SS-6 | **窗口内计数**：窗宽以秒计，跨重启保持窗口没有意义。跨重启有意义的部分（窗口起点与累计值）落在 `usage_counters`（DD-4） |
| 10 | `Router.table_` / `schema_` | SS-6 | 代码即配置（`register` 一行），落库会引入「路由表版本与代码不一致」的新故障模式 |
| 11 | 前端一切状态（`#store` / `#form` / `#regs` …） | SS-7 | 前端状态是**服务端状态的投影**，唯一例外（登录令牌）走 `localStorage`，不属于服务端数据设计 |

**一条需要显式说明的边界 —— 会话不跨重启恢复**

`sessions` 表**持久化**（`saveSession` 是 `IStore` 方法），但它的用途**限定为审计与会话数统计**，**不作为进程重启后的会话恢复依据**。理由：状态图① 明确「`SessionContext` 不可能有会话但没有内核」（组合关系 R-05 保证），而内核是进程内对象、不持久化；若允许「按旧令牌恢复会话」，就会造出**「令牌有效但内核为空」这一非法态**。因此：

> `SessionService` 启动时 `live_` **恒为空**，所有旧令牌一律按 `Unauthorized` 处理。旧 `sessions` 行留在表里做审计，但**不参与活跃判定**。

这也解释了为什么「活跃会话数」的判定必须带时间条件（`expires_at > now()`，DD-4）：重启后没有清理动作，旧行靠 `expires_at` 自然失效。

#### 7.1.4 持久化边界的三条判据

提炼成可复用的判据，供将来新增类时套用：

| 判据 | 内容 | 反例（不满足即不持久化） |
| --- | --- | --- |
| **①** | 该数据是否在**两个会话之间**仍需要存在？ | `ArchState` —— 同一次执行内有效 |
| **②** | 该数据是否是**某个持久实体的组成部分**？（随它整体存取） | `TestCase` 是 `TestSuite` 的组成部分 → **要**持久化（判据②正向命中，即使它没有独立方法） |
| **③** | 该数据是否**可由已持久化的数据重建**？ | `DecodeTable` 可由 `IsaSpec` 重建；`Usage.sessions` 可由 `sessions` 表算出 |

> 判据 ③ 最容易被忽略。「可派生」与「冗余一列」的差别在评审时看不出来，但冗余列一旦不一致就无法判断谁是对的 —— 所以本设计**不为派生值设列**（DD-4）。

### 7.2 存储方式与组织方式

#### 7.2.1 持久存储机制的选择

SAD 6.1 已定两种形态的制品：云端是 **PostgreSQL 16 实例 + 初始化 DDL**，本地是 **`workspace.db`（SQLite 单文件）**，同一套源码只靠配置项区分（SA-10 的 `DbDriver` 抽象）。那为什么不干脆用「文件」？

| 候选机制 | 否决 / 采纳的理由 |
| --- | --- |
| 纯文件（每用户一个 JSON 文件） | **否决**。① 隔离要靠文件名约定，而 SA-05 要的是「逐语句谓词」—— 文件方案里这条约束无处落地，安全从「机制」退回「纪律」；② 报告与分歧需要按时间 / 按用例集列表查询（UI-06），文件方案要自己实现索引；③ 并发写入需自己加锁 |
| 嵌入式键值库（如 LMDB） | **否决**。多一层非关系模型，而本设计的数据天然是关系型的（用户 → 工作区 → 用例集 → 用例） |
| **关系数据库（PostgreSQL / SQLite）** | **采纳**。① 隔离谓词可直接写进 SQL，与 `DbStore::scoped` 严丝合缝（SA-05）；② 列表查询、唯一约束、外键完整性由数据库保证；③ SQLite 单文件足以支撑本地单机形态，且与 PG 的差异被 `DbDriver` 收敛到方言层 |

> **补充理由**：FR-8.3 要求交付「接口文档与调用示例」，而示例脚本（UC-13）会产生大量数据。关系库让「配额统计」「资源占用」（UC-14）这类聚合查询直接由 SQL 完成，不必把数据全量读进内存再统计。

#### 7.2.2 双形态的 DDL 差异（SA-10 的落点）

同一份逻辑模式在两套数据库上的类型映射差异，全部由 `DbDriver`（`DriverKind` ∈ {`Postgres`, `Sqlite`}，E-13）承担：

| 逻辑类型 | PostgreSQL | SQLite | 差异处理 |
| --- | --- | --- | --- |
| 主键 / 外键标识 | `BIGINT` | `INTEGER` | SQLite 的 `INTEGER PRIMARY KEY` 即 rowid 别名；本设计**不依赖自增**（G-2），故差异仅剩类型名 |
| 字节串（映像、散列、盐） | `BYTEA` | `BLOB` | 同义 |
| 变长文本 | `VARCHAR(n)` / `TEXT` | `TEXT` | SQLite 不强制长度；`VARCHAR(n)` 仅作**声明性约束**，写入侧由 `Router.bind` 的 Schema 先行校验 |
| 时间戳 | `TIMESTAMPTZ` | `TEXT`（ISO-8601 UTC，如 `2026-10-13T02:37:06Z`） | SQLite 无原生时间类型；选 ISO-8601 文本是因为它**字典序即时间序**，`ORDER BY` 与 `>` 比较都正确 |
| 布尔 | `BOOLEAN` | `INTEGER`（0/1） | 读写由 `DbDriver` 转换 |
| 结构化文档列 | `JSONB` | `TEXT`（JSON 文本） | PG 可对 JSONB 建 GIN 索引；本设计的文档列**都不作为查询条件**（G-3），故两者行为一致 |
| 枚举 | `SMALLINT` | `INTEGER` | 一律存小整数，**不用 `ENUM` 类型** —— 枚举增删在 PG 上是 DDL 变更，在应用侧只是常量表加一行 |
| UPSERT | `INSERT … ON CONFLICT … DO UPDATE` | 同语法（SQLite 3.24+） | **无差异** |

**9 个逻辑类型、7 处需要 `DbDriver` 转换**，其余（`SELECT` / `WHERE` / `ORDER BY` / 事务控制）两库语法一致。

> **声明性约束的落地差别**：PG 侧用 `CHECK` / `UNIQUE` / `FOREIGN KEY` 由数据库强制；SQLite 侧需 `PRAGMA foreign_keys = ON`（默认关闭）才生效外键。故启动序列里必须含这条 PRAGMA（见 7.4.6）。

#### 7.2.3 「关系列」与「JSON 文档列」的取舍口径

| 候选 | 裁决 | 理由 |
| --- | --- | --- |
| `TestCase` 的身份与查询字段（`name` / `program_hash` / `timeout_steps` / 执行序） | **关系列** | 会被 `ORDER BY seq_no` 使用；`checksum` 校验要按字段逐项比对 |
| `ExpectedSpec` | **JSON 列**（`expect_blob`）+ 类型标签列（`expect_mode`） | 它是二选一的联合（`finalAssert` 或 `sequence`），拆列会出现「一半列恒为 NULL」的稀疏表；且只被整体读写 |
| `CaseResult.diffFields` | **JSON 列** | 只在失败现场的详情里整体展示，不查询 |
| `CaseResult.snapshot`（`StateSnapshot`） | **JSON 列**（`snapshot_blob`）且**独立成列** | 列表页不取、详情页才取；独立成列使「按需读取」成为一条 `SELECT` 列选择，而不是「读完再扔掉」（DD-3） |
| `Program`（`image` 字节 + 5 个字段） | **JSON 列**（`program_blob`），`image` 用 base64 内嵌 | 纯值对象，无子项、不查询 |
| `SessionConfig` | **JSON 列**（`config_blob`） | 同上 |
| `TestSuite.tags` | **JSON 数组列** | 只作展示与筛选提示，不参与 SQL 条件 |
| `TestSuite.cases_` | **关系子表**（`test_cases`） | 见 DD-2 |
| `Divergence.attribution` | **关系列**（`attr_category` / `attr_by` / `attr_at` / `attr_note`） | 归因类别要支持「按归因统计」（FR-7.4），拆成列才能聚合 |

**结论**：**11 张表 + 7 类文档列**（`program_blob` / `config_blob` / `tags` / `expect_blob` / `diff_fields` / `snapshot_blob` / `field_diffs`）。

#### 7.2.4 关系与键的落点规则

技能规定「1:1 或 1:n：在 n 端表中加入外键；n:m：新增交叉表」。按 6.2.3 的关系清单取出**跨持久实体**的部分：

| 关系 | 类别 | 落点 | 依据 |
| --- | --- | --- | --- |
| `User` 1:1 `CredentialRow` | 1:1 | `credentials.uid`（PK / FK） | DD-1；与 `users` 主键同值 |
| `User` 1:1 `Usage`（窗口部分） | 1:1 | `usage_counters.uid`（PK / FK） | R-21 的延伸 |
| `User` 1:n `SessionRow` / `Workspace` / `TestSuite` / `TestReport` / `Divergence` | 1:n | 各表的 `owner_id` → `users.uid` | n 端加外键 |
| `Workspace` 1:n `SessionRow` | 1:n | `sessions.ws_id` → `workspaces.ws_id` | 可空（首次登录尚无工作区行） |
| `Workspace` 1:n `TestSuite` | 1:n | `test_suites.ws_id` → `workspaces.ws_id` | 见 DD-8（基数由 0..1 修正为 n） |
| `Workspace` 1:n `Breakpoint` | 1:n | `breakpoints.ws_id`（**不设外键**） | 见 DD-6 |
| `TestSuite` 1:n `TestCase` | 1:n（组合） | `test_cases.suite_id` → `test_suites.suite_id`，CASCADE | R-07；见 DD-2 |
| `TestReport` 1:n `CaseResult` | 1:n（组合） | `report_cases.report_id` → `test_reports.report_id`，CASCADE | R-08；见 DD-2 |
| `JobEntry` 1:n `Divergence` | 1:n（**逻辑**） | `divergences.job_id`（**无外键**） | 任务不持久化（7.1.3），只存标识 |

**n:m 为零**：类设计已判定全系统不存在 n:m 关系。**因此本步不新增任何交叉表** —— 这是「技能规定的 n:m 分支不适用」的显式记录，避免评审时被读成遗漏。

**共 14 处关系、13 个数据库级外键、1 处逻辑引用。级联策略**：

| 场景 | 策略 | 理由 |
| --- | --- | --- |
| 删除用户 → 其凭据 / 用量 / 会话 / 工作区 / 用例集 / 报告 / 断点 / 分歧 | `ON DELETE CASCADE` | 用户在 `status = Disabled` 之外**不提供删除**（UC-14 只有「停用」），级联仅为完整性兜底 |
| 删除工作区 → 会话的 `ws_id` | `ON DELETE SET NULL` | 会话是审计记录，不应因工作区消失而消失 |
| 删除工作区 → 用例集 | `ON DELETE SET NULL` | 用例集可在多个工作区间复用（`test_suites.ws_id` 可空） |
| 删除用例集 → 用例 | `ON DELETE CASCADE` | 组合关系 R-07：「子项不独立存在」 |
| 删除报告 → 用例结果 | `ON DELETE CASCADE` | 组合关系 R-08 |
| 删除用例 → `report_cases` 的明细 | **不设 `case_id` 外键** | 用例被删后，历史报告仍需保留「当时跑了哪些用例、结果如何」，否则历史报告会残缺（见 7.3.10） |

> - `sessions` = `SELECT COUNT(*) FROM sessions WHERE owner_id = :u AND ended_at IS NULL AND expires_at > now()`；

>
> 若将来需要长期留存完整现场，正确的做法是**新增一个可选列**而不是现在预留 —— 这符合「不为不确定的需求预留列」的原则。

#### 7.4.3 事务边界

需要原子性的只有两处（其余操作都是单语句）。

**事务 T-1 —— `putWorkspace`（保存工作区，UC-12）**

| 步 | 语句 | 失败时的效果 |
| --- | --- | --- |
| 1 | `SELECT version FROM workspaces WHERE ws_id = :id AND owner_id = :u` | 取当前版本 |
| 2 | 比较 `:expected_version`（乐观并发，7.4.5） | 不等 → `Err(VersionConflict)`，**回滚** |
| 3 | `INSERT … ON CONFLICT (ws_id) DO UPDATE` 主表（`version + 1`，重算 `size_bytes`） | |
| 4 | `DELETE FROM test_cases WHERE suite_id IN (SELECT suite_id FROM test_suites WHERE owner_id = :u AND ws_id = :id)` | |
| 5 | UPSERT `test_suites` 一行（**DD-8 后为多行**） | |
| 6 | 批量 `INSERT test_cases` | |
| 7 | `COMMIT` | |

**为什么要事务**：第 4 ~ 6 步是「先用例集整体替换」（UC-12 的保存语义）。任何一步失败都会留下**半套用例** —— 而 `checksum` 的语义是「整套的校验和」，半套数据会让校验**永久失败**。用事务把 4 ~ 6 圈起来后，要么整套新用例集生效，要么整套旧数据保留。

**事务 T-2 —— `saveReport`（报告落库，UC-08）**

| 步 | 语句 |
| --- | --- |
| 1 | `INSERT INTO test_reports (…)` |
| 2 | 批量 `INSERT INTO report_cases (…)` |
| 3 | `COMMIT` |

**为什么必须原子**：`test_reports.total` 与 `report_cases` 的行数必须一致，否则 UI-06 会显示「10 个用例、7 条明细」。事务是这对不变量唯一的强制点。

**不需要事务的操作及理由**

| 操作 | 理由 |
| --- | --- |
| `saveSession` / `dropSession` | 单语句 |
| `saveDivergence`（批量） | 虽是批量，但分歧是**追加型**记录，部分写入不会造成不一致（每条独立完整）。用单语句多值 `INSERT` 即可 |
| `saveBreakpoints`（DELETE + INSERT） | 两步之间即使中断，后果是「断点表为空」—— 而空断点是**合法初值**。故不加事务，避免为一个可接受的状态付出额外开销 |

#### 7.4.4 验证操作（11 项）

| # | 验证 | 时机 | 落点 | 失败处理 |
| --- | --- | --- | --- | --- |
| V-01 | **用户存在性** | 登录 | O-03 `findCredential` 返回空 | `Err(Unauthorized{NoSuchUser})`；**但先执行哑元 KDF**，耗时与存在路径相当 |
| V-02 | **口令正确性** | 登录 | 用 `salt` / `iterations` / `kdf` 重算后比对 `secret_hash` | `Err(Unauthorized{BadPassword})` |
| V-03 | **账号状态** | 登录 | O-03 返回的 `status` | `Err(Unauthorized{Disabled})` |
| V-04 | **重名** | 创建 / 另存工作区 | `UNIQUE (owner_id, name)`（IX-04） | 捕获唯一冲突 → `Err(NameTaken)`（UC-12 E1 提示覆盖或另存） |
| V-05 | **版本一致** | 保存工作区 | T-1 第 1 ~ 2 步 | `Err(VersionConflict)`；UC-12 E3 的「数据版本不兼容」也走此路径 |
| V-06 | **配额** | 保存工作区 / 发起请求 | `usage_counters`（O-06）+ `IConfig`；判定在 `AccessGuard` | `Err(QuotaExceeded)`；UC-12 E2 与 UC-01 E2 共用 |
| V-07 | **存储上限** | 保存工作区 | 新 `size_bytes` + 现有 `SUM(size_bytes)` 与 `q_bytes` 比较 | `Err(QuotaExceeded)`；**在事务提交前判定**，避免先写后删 |
| V-08 | **引用完整性** | 所有写入 | 外键约束（7.3.13） | 数据库错误 → `Err(Internal)`；正常流程不应出现（由应用侧标识生成保证） |
| V-09 | **用例集完整性** | 加载工作区 | `checksum` 与重算值比对（C-12） | `Err(ChecksumMismatch)`；UC-12 E3 的另一条路径 |
| V-10 | **数据格式版本** | 加载工作区 | `version` 与当前支持区间的比对 | `Err(VersionUnsupported)`；UC-12 E3 的第三条路径 |
| V-11 | **枚举取值合法** | 每次写入 | `Router.bind` 的 Schema 校验（写入侧） | `Err(BadRequest)`；**不依赖数据库的 CHECK 约束**（双形态下 CHECK 的行为差异不值得引入） |

> **为什么枚举合法性由应用侧而不是 `CHECK` 约束验证**：`CHECK` 在 PG 与 SQLite 上的报错信息、以及「加一个枚举值要改 DDL」这件事，都会让双形态的维护成本上升；而写入路径的唯一入口是 `Router.bind`，在那里校验一次即可。

#### 7.4.5 并发与版本控制

| 场景 | 机制 | 落点 |
| --- | --- | --- |
| 同一工作区被并发保存 | **乐观并发**：`Workspace.version` 作为前提条件（T-1 第 2 步） | UC-12 E3 的「版本不兼容」提示 |
| 同一会话的心跳写 | **写入节流**：`tHeartbeat` 内不重复落库（7.3.5） | 降低写放大 |
| 报告落库与查询并发 | 事务 T-2 的原子提交；`queryReports` 读到的是已提交快照 | UI-06 不会看到「用例数对不上」的中间态 |
| 分歧批量写与按任务查询 | 单语句多值 `INSERT`；同一任务的记录由同一调用写入 | `queryDivergence` 要么看不到该任务、要么看到全套 |
| 会话数上限的统计 | `live_`（内存真值）与 `COUNT(sessions)`（派生）**可能短暂不等** | 见下 |

> **最后一行要说清**：`AccessGuard.checkQuota` 判定并发会话数时以**内存 `live_` 为准**（它是会话的权威视图），而 `Usage.sessions`（展示用，UC-14）走 SQL 派生。两者在 `tHeartbeat` 窗口内可能差 1 ~ 2 —— 展示口径与限额口径本就允许不同（前者给管理员看趋势，后者是硬约束），但**必须只有一个权威**：权威是 `live_`。

##### 7.4.5.1 进程内并发（内存共享结构的保护）

上表全部是**数据库侧**的并发口径；服务端为「事件循环 + 线程池（网关 / 鉴权 / 路由）」（SAD 8.1），因此还有一处必须交代：**进程内可变共享结构**。它们的保护方式与「内核线程封闭」并列说明如下：

| 共享结构 | 归属 | 访问特征 | 保护方式 |
| --- | --- | --- | --- |
| `SessionService.live_` | SS-5 | 登录 / 登出 / `touch`（心跳，高频）/ `reap`（定时）/ `checkQuota` 读 | **按会话分片的读写锁**：`std::shared_mutex` 保护表结构，`touch` 只改 `SessionContext.lastSeen`（命中分片内的 `atomic` 时间戳），使高频心跳不争全局锁 |
| `TestService.jobs_` / `DiffService.jobs_` | SS-5 | 任务建立 / 状态推进 / 取消 / 完成时清理 | **各自一把 `std::mutex`**（两个服务各自持有自己的表，互不可见，见 R-10 / R-11）；单次持锁只做 map 的读写，**不在锁内做执行** |
| `AccessGuard.rate_` | SS-6 | 每个请求一次自增与窗口判定 | **原子计数**（`atomic<uint64_t>`）；窗口滚动用「当前秒槽 + 上一秒槽」两个原子槽表达，不做加锁 |
| 内核（`EmulatorCore` 及 `ArchState` / `Trace`） | SS-1 | 只被**单个会话的执行线程**访问 | **线程封闭**：`SessionContext` 保证同一时刻只有一个执行流进入 `run()`；`ICoreService` 的方法不做内部加锁（这也是 `CancelToken` 用 `atomic<bool>` 而非锁的原因 —— 它是**唯一的跨线程读**） |

**三条口径**：① 「无状态服务单例」（SAD 8.4）说的是**不持有业务数据**（用户 / 工作区 / 报告都不在服务里），**不等于可以无锁复用** —— 上表三处都是服务持有的**运行期簿记**，属"基础设施状态"而非业务状态；② 加锁的粒度**只在表结构操作**上，执行体（内核循环、子进程等待）一律在锁外，避免长持锁；③ 数据库侧与内存侧的权威不同（会话数以 `live_` 为准），已在上面说明。

| 1 | 按 `IConfig.dbDriver()` 选择连接（`DriverKind`） | SA-10 的落点 |
| 2 | SQLite：`PRAGMA foreign_keys = ON` | **必须**，否则外键不生效（7.2.2） |
| 3 | 检查模式版本（统一的 `schema_version` 表） | 版本不符 → 走迁移或拒绝启动 |
| 4 | 建表（`CREATE TABLE IF NOT EXISTS` × 11） | 幂等；DDL 由 `DbDriver` 生成以吸收类型差异 |
| 5 | 建索引（`CREATE INDEX IF NOT EXISTS` × 9） | 幂等 |
| 6 | 种子数据：无 `Admin` 用户时插入一个 | 本地形态下 `authEnabled = false` 也会用到管理员视角的 UC-14 |
| 7 | `live_` 空启动 | 见 7.1.3：不恢复任何会话 |

> **第 3 步的「模式版本」与 `Workspace.version` 不是一回事**：前者是**数据库结构的版本**（与迁移脚本对应），后者是**单行数据的版本**（乐观并发）。同名不同义，故统一用一张 `schema_version` 表（不用 `PRAGMA user_version`，避免只在 SQLite 上可用）。

## 8 设计模式应用

### 8.1 选型原则

本章只登记**已经落在具体设计元素上**的模式，遵循三条原则：

1. **有实际收益才用**。每个模式必须能指出「不用它会怎样」；指不出的不写。
2. **优先用语言特性表达，而不是用结构表达**。C++17 的枚举、`const`、`variant` 已经能表达很多模式语义，不必为此引入基类或虚函数（这也是 D-6 零继承的必然结果）。
3. **模式与体系结构决策对得上**。凡是本章列出的模式，都能追溯到一条 SA-xx 或一条设计总则。

### 8.2 采用的设计模式

| # | 模式 | 类型 | 落点（设计元素） | 不用它会怎样 |
| --- | --- | --- | --- | --- |
| 1 | **适配器 Adapter** | 结构型 | `ToolchainAdapter` / `RefSimAdapter` / `DbDriver` | 工具链与数据库的差异会扩散到服务层与业务代码，双形态要写两套 |
| 2 | **桥接 Bridge** | 结构型 | `IDecodeTable`（抽象）↔ `DecodeTable`（实现）；`IStore` ↔ `DbStore` | 「内核需要译码」与「译码怎么算」被绑死，换一套 ISA 表示要改内核 |
| 3 | **策略 Strategy** | 行为型 | `IAssembler` / `IRefSim` / `IConfig` / `DiffScope.mode`（两种判定模式） | 每种可替换能力都要 `if-else` 分支，且分支写在调用方 |
| 4 | **外观 Facade** | 结构型 | `ICoreService`（对 SS-1 的 4 个构件）；`SessionService`（对会话上下文）；`HttpGateway`（对网络层） | 调用方要自己组合 4 个构件、自己管生命周期 |
| 5 | **静态工厂 / 简单工厂** | 创建型 | `DecodeTable::build` / `DiffScope::preset` / `Divergence::make` | 不可变对象的构建逻辑散落在调用方，且无法保证「构建即合法」 |
| 6 | **建造者 / 组合根** | 创建型 | `Bootstrapper::build`（SA-08） | 装配逻辑散落到各服务的构造里，依赖顺序无处保证；`new` 会出现在多处 |
| 7 | **备忘录 Memento** | 行为型 | `StateSnapshot` + `ICoreService.restore`（UC-07 回退、UC-12 恢复） | 状态恢复要由调用方逐字段抄回来，`ArchState` 的封装被打破 |
| 8 | **命令 / 可撤销操作** | 行为型 | `WriteOp` + `Trace.rewindTo`（逆序撤销） | 回退要实现成「重放前半段」，代价是 O(n) 而非 O(回退步数) |
| 9 | **状态** | 行为型 | `RunState`（E-01）/ `JobState`（E-14）驱动合法操作集合 | 控制条按钮可用性（C-04）要写成散落的布尔判断 |
| 10 | **观察者 / 发布订阅** | 行为型 | `HttpGateway.push` + `WsSession` + `Event`（FR-6.4 批量进度） | 批量执行进度只能靠前端轮询，违背 FR-6.4 的"主动推送" |
| 11 | **单例（受限形式）** | 创建型 | `Bootstrapper` 持有的唯一实例（`IsaLoader` / `CompareEngine` / 7 个服务） | 无状态能力会被重复构造，或退化为全局变量 |
| 12 | **享元 Flyweight** | 结构型 | `DecodeTable`（按 `SpecId` 复用的**不可变**共享对象，R-04） | 每个会话各建一份译码表，启动成本与内存都翻倍 |
| 13 | **保护代理 Protection Proxy** | 结构型 | `ICoreService`（R2 后成为 `ArchState` 写入口的唯一门面） | 「谁能改架构状态」无法在类型系统上约束（D-2 的动机） |

**逐条说明（只展开需要解释的）**

- **① 适配器**是本设计用得最重的一个：SA-06 规定「外部系统一律经端口—适配器隔离」，落地为 SS-4 的两个适配器 + SS-8 的 `DbDriver`。三个适配器都把「外部世界的差异」封闭在一层里，且都**只经接口被调用**（I-05 / I-06 / `IStore`）。
- **② 桥接与③ 策略的区别**在本设计里很清晰：**桥接**分离的是「抽象」与「实现」两棵独立的继承结构（`IDecodeTable` 的调用方是内核，实现方是 ISA 抽象层，两者可各自演进）；**策略**替换的是同一抽象下的**算法**（`IRefSim` 换一个参考模拟器、`DiffMode` 换一种判定方式）。这个边界让 SA-01 的依赖倒置不会被误读成"策略模式"。
- **⑥ 建造者**在这里的具体形态是**组合根**：`Bootstrapper::build` 是全项目唯一出现 `new` 的地方，它按 `IConfig` 选驱动、按依赖顺序装配整张对象图。这条约定可用 `grep -n "new " src/` 在 CI 里强制。
- **⑨ 状态**没有用多态的 `State` 类，而是用**枚举 + 判定表**。理由：状态集合封闭（`RunState` 六取值、`JobState` 五取值，都由需求固定），多态会引入 6 个类而收益为零；这正是选型原则 2 的体现。
- **⑪ 单例**用的是**受限形式**：单例语义由「组合根持有唯一实例」提供，**不用静态 `getInstance()`**。这样单元测试可以替换实例（NFR-I2 的要求），而真正的静态单例做不到。
- **⑬ 保护代理**是 D-2 / R2 的直接结果：`ArchState` 降为档 2 之后，`ICoreService` 成为它写入口的唯一门面，调用方拿不到 `ArchState&`，破坏 SA-13 的写法在编译期就不存在。

### 8.3 未采用的设计模式及理由

| 模式 | 为什么不采用 |
| --- | --- |
| **模板方法 Template Method** | 需要继承。本设计**零继承**（D-6）：35 个构件之间没有「是一种」的关系。骨架复用改由「组合 + 接口注入」表达（如两个适配器共用 `IProcessRunner`） |
| **装饰器 Decorator** | 需要同型对象的层层包装，而本设计的能力扩展点（日志、限额、鉴权）都被**收敛到唯一落点**（SS-8 / `AccessGuard`），不需要"一层层加" |
| **职责链 Chain of Responsibility** | 请求处理是**固定三段**（鉴权 → 路由 → 服务），不是「谁先处理谁负责」的链；固定链写成顺序调用比链式更清晰、更快 |
| **原型 Prototype** | 值类型本身就是「复制即克隆」；引用语义类（内核族）不允许被克隆（每会话一个实例，R-05） |
| **访问者 Visitor** | 需要对封闭的类型集合做多种遍历；本设计的遍历场景只有比对（`CompareEngine`），它按字段掩码遍历而非按类型分发 |
| **解释器 Interpreter** | ISA 描述确实是一套「小语言」，但它的解释结果是**直表**（`DecodeTable.rows_`）而不是语法树 —— 直表在热路径上是 O(1)，语法树不是 |
| **抽象工厂 Abstract Factory** | 只有一族产品（按 `DriverKind` 选驱动），简单工厂足够；`Bootstrapper` 已经承担了「按配置选实现」的职责 |
| **多例 Multiton** | 无状态服务共享单例即可，可变状态都在 `SessionContext` 里按会话隔离，不需要按 key 的多例 |

### 8.4 设计模式与设计原则的对应

| 设计原则 / 决策 | 支撑它的模式 |
| --- | --- |
| P1 抽象边界优先（T3） | ② 桥接、③ 策略 |
| P2 关键路径不做进程 / 网络跳转（T2） | ④ 外观（`ICoreService` 是同进程门面）、⑫ 享元（译码表共享） |
| P4 外部系统一律经端口—适配器（SA-06） | ① 适配器 |
| P5 依赖单向、仅相邻层 | ② 桥接（`IDecodeTable` 的依赖方向反转）、⑬ 保护代理 |
| P6 复用优先 | ⑫ 享元、⑪ 单例（无状态能力共享） |

| SA-03 每会话一个内核、随会话销毁 | ⑥ 组合根（装配）、⑦ 备忘录（状态可存可恢复） |
| SA-04 比对引擎被两处复用 | ⑪ 单例（无状态共享）、⑫ 享元 |
| SA-05 限额与隔离不进内核 | ⑬ 保护代理、④ 外观 |
| SA-13 差分回退 | ⑦ 备忘录、⑧ 命令 / 可撤销操作 |
| 类设计 G-3 全项目只有一处 `new` | ⑥ 建造者 / 组合根 |
| 类设计 G-4 函数式核心 | ⑤ 静态工厂（`CompareEngine` 连属性都没有） |
| 数据设计 G-1 谓词列统一（D-5） | ① 适配器（`DbDriver` 的方言层）+ `DbStore.scoped` 的统一组装 |

> **一句话总结**：本设计的模式使用集中在**边界隔离**（适配器 / 桥接 / 门面 / 代理）与**对象装配**（工厂 / 组合根 / 单例 / 享元）两组，而**没有**使用任何要求继承结构的模式 —— 这是 35 个构件零继承这一决策的必然结果，也是「强内聚、松耦合」能够用类型系统而不是纪律来保证的原因。
