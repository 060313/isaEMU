## 四、③ 优化性

**评审要点**：是否以充分优化的方式实现所有软件需求项，尤其是关键性软件需求。

### 4.1 关键需求的优化手段

| 关键需求 | 优化手段 | 是否落到具体决策 |
| --- | --- | --- |
| NFR-Q1 单步 ≤ 100 / 300 毫秒、10⁷ / 10⁶ 条每秒 | 内核以静态库链入同进程（SA-02）；状态增量而非全量推送（SA-11）；轨迹记录可开关，关闭时热路径不增开销 | 是 |
| FR-1.1 描述驱动 vs NFR-Q1 的吞吐要求 | 译码表**预构建 + O(1) 查表**，不做每条指令解析描述文件（5.4.4 `DecodeTable` 的引入理由） | 是 |
| NFR-Q2 10⁸ 条不漂移、单用例失败不牵连 | 每会话一个独立内核实例、线程封闭（SA-03）；运行期异常在内核内被 `TerminationGuard` 拦住，不靠进程隔离兜底 | 是 |
| FR-6.5 两种判定模式复用同一引擎 | 比对能力独立成子系统 SS-3，被 `TestService` 与 `DiffService` 共用（SA-04）；迭代三绑定交付 UC-08 与 UC-10 | 是 |
| NFR-Q5 限额与隔离 | 限额前置在 SS-6 `AccessGuard`（SA-05）；指令条数上限以下发参数形式随运行请求传入，不让内核持有配额状态；隔离落在每条数据访问语句上 | 是 |
| NFR-I2 内核可独立测试 | 内核零第三方链接，由构建期规则二机械保证（7.3） | 是 |

### 4.2 发现与处理

| 编号 | 严重度 | 问题 | 处理 | 状态 |
| --- | --- | --- | --- | --- |
| ③-1 | **高** | **FR-4.4「回到任意已执行步」在体系结构层缺失实现策略**。原文档只在附录 B.1 写了"`Trace`（差分回退）"六个字：全量快照为何不可行、差分记录从哪来、内存量级如何、轨迹是否需要裁剪——均未交代。这是一个**会直接影响详细设计的结构性决策**，留白会让 `sdd` 阶段自行发明方案 | 新增 **5.6.5 历史回退的实现策略**：明确采用差分 / 日志式回退、复用 `Trace` 已记录"本步引发的写操作"（与 FR-3.3、FR-7.2 共用同一份数据形态，不额外引入机制）、说明内存量级与轨迹长度的关系、要求轨迹**可裁剪**（与 NFR-Q2 的 10⁸ 条连续执行直接相关）、说明与 NFR-Q1 的关系（关闭轨迹时同时关闭回退）。同步登记为决策 **SA-13** | **已修正** |
| ③-2 | 中 | SA-01（依赖倒置）只写了方案的**限制**，未给出"何时需要重新审视该决策"的判据，可扩展性的边界因此不可操作 | 在 5.6.1 补"**演进触发条件**"表：三种情形（新增指令全落在既有类别内 / 引入少数新类别 / 第二套 ISA 的架构状态模型根本不同）分别对应三种架构动作 | **已修正** |

**③ 结论：通过**（关键需求均有明确且已书面化的优化手段；1 条高风险留白已补）。

## 五、④ 可扩展性

**评审要点**：体系结构设计是否易于扩展，以应对软件需求的变化。

### 5.1 需求变化类型与设计的应对

| 变化类型 | 受影响范围 | 设计给出的应对 |
| --- | --- | --- |
| 新增一款 ISA（NFR-I1 的核心目标） | 仅 SS-2 | SA-01 依赖倒置：只需给出新的 `DecodeTable` 实现 + 描述文件；内核二进制不变 |
| 新增一条 RV32I 指令语义 | 仅 ISA 描述文件 | 见 5.6.1 之 (a)：纯数据变化 |
| 新增指令的**操作类别** | SS-1 的语义模板表 | 见 5.6.1 之 (b)：改动集中、执行循环不变 |
| 调整比对子集 | 仅配置 | SS-3 `DiffScope` 可配置（FR-7.2 / NFR-I1） |
| 新增 / 修改对外接口 | 仅 SS-6 `Router` | 路由机制独立于鉴权与业务（5.4.4 `Router` 的引入理由） |
| 新增视图 | 仅 SS-7 | `AppShell` 提供路由与 API 客户端的统一外壳（5.4.4） |
| 更换数据库 | 仅 SS-8 持久化服务 | SA-10：`DbDriver` 抽象适配双数据库 |
| 更换参考模拟器 | 仅 SS-4 | 端口—适配器隔离（P4 / SA-06）；本期锁定 Spike 是范围收敛而非结构限制 |
| 新增第二套持久化形态 | SS-8 + 配置 | SA-09：形态由配置区分，不出现"if 本地 / else 云端" |

### 5.2 发现与处理

| 编号 | 严重度 | 问题 | 处理 | 状态 |
| --- | --- | --- | --- | --- |
| ④-1 | 中 | **内核实例内存驻留所带来的扩展边界未登记**。SA-02 / SA-03 决定内核实例常驻应用进程内存，这是 NFR-Q1 的必然结果，但也意味着**单进程内存上限即系统会话上限**；原文档没有把这一点写出来，读者会误以为横向扩展是免费的 | 在 8.4 补"**已知演进点**"：本期需求（LIM-06 单机部署、无横向扩展要求）不构成问题；若未来要求多机横向扩展，需把"会话亲和"从进程内升级为可路由的会话池，并明示这是一次结构性改动 | **已修正** |
| ④-2 | 低 | NFR-I1 的两项可扩展性要求（ISA 抽象边界、比对子集可配置）均已给出可替换点 | — | 无需处理 |

**④ 结论：通过**（主要变化类型均有局部化的应对点；扩展边界已如实登记）。

## 六、⑤ 详略程度

**评审要点**：设计内容是否详略得当，既不过于详尽而脱离体系结构，也不过于粗略而影响后续详细设计。

### 6.1 粒度检查

| 检查项 | 结果 |
| --- | --- |
| 是否展开到类内部实现 | 否。5.5.2 只给构件职责与承载需求；具体类、属性、方法均标为 `sdd` 阶段的产出 |
| 是否展开到数据结构字段 | 否。5.6.5 只给回退策略与内存量级，字段级设计留给 `sdd` |
| 是否出现伪代码 / 算法 | 否。唯一两处涉及机制（5.6.1 译码表预构建、5.6.5 差分回退）都属**结构级决策**（决定了模块边界与内存约束），不是实现细节 |
| 是否过粗以致无法指导详细设计 | 否。8 个子系统 / 35 个构件 / 13 条决策 / 9 张接口表均给出到"构件 + 接口"粒度；附录 B 给出逐需求落点 |
| 章节配比 | 第 5 章（逻辑视点）316 行，第 6 ~ 8 章（部署 / 开发 / 运行）共 216 行，符合"逻辑视点为主、其余视点为辅"的合理配比 |

### 6.2 保留的重叠（不成问题）

| 编号 | 现象 | 判断 |
| --- | --- | --- |
| ⑤-1 | 6.7（部署对结构约束的影响）与 8.4（资源边界与生命周期）在"同进程约束"上有内容重叠 | **保留**。两处属不同视点（部署 vs 运行）的合理重述，符合"多视点"方法的要求；已在 8.4 与 6.7 之间建立交叉引用 |
| ⑤-2 | 2.2 与需求规格说明书 3.1 的重复度较高 | **保留**。技能明确要求"与需求规格说明书的系统概述保持一致"，重复是其必要条件而非冗余 |
| ⑤-3 | 5.4.4 同时列了 13 行新增元素表与一段计数说明 | **保留**。计数说明是应"评审可核查"的要求后加的，用于消解与上游计数口径的潜在冲突 |

### 6.3 遗留的非阻塞项

| 编号 | 内容 | 归属 |
| --- | --- | --- |
| ⑤-4 | NFR-Q4 的"最近两个大版本"在前端侧的具体构建目标（浏览器目标设定）未在 7.2 明确 | 属实施细节，随 `sdd` 或编码阶段确定 |

**⑤ 结论：通过**（粒度为"构件 + 接口 + 结构级决策"，既未下探到实现，也不至于无法指导详细设计）。
